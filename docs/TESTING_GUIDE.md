# Testing Guide

A module is not complete until its functionality and tests pass. Tests run against **PostgreSQL** (`pos_test`), never SQLite, because the system relies on PostgreSQL behaviour (row locks, partial indexes, `NUMERIC`, triggers).

## Backend (PHPUnit 12)

```powershell
cd backend
php artisan test                         # all suites
php artisan test --testsuite=Modules     # module tests only
php artisan test --filter=Checkout       # by name
php artisan test --parallel              # once suites grow
```

Suites (`phpunit.xml`):

| Suite | Location | Contents |
|-------|----------|----------|
| `Modules` | `app/Modules/*/Tests/**/*Test.php` | Module unit and feature tests (primary location) |
| `Unit` | `tests/Unit` | Cross-cutting unit tests |
| `Feature` | `tests/Feature` | Cross-module / end-to-end API flows |

Test environment: `DB_CONNECTION=pgsql`, `DB_DATABASE=pos_test`, array cache, sync queue, array mail. Credentials come from `backend/.env` (`DB_USERNAME`/`DB_PASSWORD`).

PostgreSQL-only tests (`StockLockingTest`, since E8a `CheckoutConcurrencyTest` and since E8b `PromotionConcurrencyTest`: two real connections, committed data via `DatabaseTruncation`) skip themselves on other drivers — 4 skips on SQLite as of E10a (E9 and E10a add none, but their CHECK constraints and the E10a append-only triggers are PostgreSQL-only too); `CheckoutConcurrencyTest` and `PromotionConcurrencyTest` have not run yet because the local PostgreSQL run is still blocked. A quick interim run without PostgreSQL is possible with `DB_CONNECTION=sqlite DB_DATABASE=:memory: php artisan test`, but it does not satisfy the definition of done below: row locks, the ledger trigger and PostgreSQL error codes are only exercised on PostgreSQL.

### What each kind of test covers

| Kind | Example | Rules |
|------|---------|-------|
| Unit (domain) | `MoneyTest`, pricing calculator, tax-inclusive/exclusive math | No database, no framework boot. Golden values for every rounding rule. |
| Feature (API) | `POST /api/v1/pos/checkout` | `RefreshDatabase`; assert envelope, status, DB state, ledger rows. |
| Authorization | Cashier cannot adjust stock | One test per policy ability, both allow and deny. |
| Tenant isolation | User of branch A gets 404 for branch B sale | Required for every tenant-scoped resource. |
| Transaction | Payment failure rolls back sale and stock | Force a failure mid-transaction; assert nothing persisted. |
| Concurrency | Two checkouts for the last unit | Separate DB connections/processes; exactly one succeeds, stock never negative. |
| Idempotency | Same `Idempotency-Key` twice | One sale, identical responses; different payload → 409. |

## Frontend (Vitest 5 + Testing Library)

```powershell
cd frontend
npm test                 # vitest run
npm run test:watch
npm run typecheck
```

- Tests are colocated: `*.test.ts(x)` next to the code.
- Timeouts (`vite.config.ts`, `src/test/setup.ts`, E8a): `testTimeout` is 20 s and Testing Library's `asyncUtilTimeout` (`findBy*`, `waitFor`) 5 s instead of 5 s / 1 s — form-heavy page tests (checkout, shipping zones, web order dialogs) drive many `user-event` steps and timed out on a loaded machine. A test that needs more is too slow and should be split.
- E8a page and logic tests: `storefront-checkout.test.tsx`, `checkout/checkout-logic.test.ts` (placement attempts and keys, error mapping, delivery labels), `storefront-cart.test.tsx` (checkout button), `features/web-orders` (`orders.test.ts`, `web-order-pages.test.tsx`), `features/shipping` (`shipping.test.ts`, `shipping-page.test.tsx`), `features/online-payments/pages/payment-methods-page.test.tsx`, `features/storefront/pages/checkout-settings.test.tsx`.

Notes for the full-stack run:
- The backend needs `STOREFRONT_DEFAULT_HOST=shop.localhost` (the seeded store) and, because the suite signs in and checks out many times a minute, `POS_API_RATE_LIMIT=1000`, `POS_AUTH_RATE_LIMIT=100`, `POS_CHECKOUT_RATE_LIMIT=1000` (the checkout page previews on every change; the default 10/min per IP makes the E8a test fail with 429) and, since E8b, `POS_COUPON_RATE_LIMIT=1000` (coupon attempts, default 10/min) and, since E9, `POS_REVIEW_RATE_LIMIT=1000` (new reviews, default 5/hour per customer). `POS_AUTH_RATE_LIMIT` (default 5) is the number of sign-in / password-reset attempts per minute per account and IP (four times that per IP); the suite signs the owner in more than five times a minute, so the default makes later specs fail with 429.
- `php artisan serve` passes only a few environment variables to its PHP process; to override `DB_*` and the settings above from the shell, run `php -S 127.0.0.1:8010 ../vendor/laravel/framework/src/Illuminate/Foundation/resources/server.php` from `backend/public` instead.
- If another dev server already holds port 5173, Playwright would reuse it (and its backend). Set `E2E_PORT=5180` and add `localhost:5180` to `SANCTUM_STATEFUL_DOMAINS` of the test backend. The same applies to any port: a leftover dev server or `php -S` from an earlier run is silently reused (Windows lets several processes listen on one port), so if results do not match a fresh seed, check for old `node`/`php` processes and pick unused ports.
- Run one project per fresh seed (`--project=desktop-chromium`): both projects post documents into the same database. The admin's mobile layout hides the sidebar links the first specs click, so the full-stack suite currently passes on desktop only (11/11 on `desktop-chromium` against a fresh seed in E8a, 10/10 in E7; the E6 product test and the E8a and E8b order tests skip themselves on mobile). In the E8b run (backend on `:8021`, Vite on `:5185`) the 6 e-commerce tests passed on desktop; the 6 POS/back-office tests failed because of the timezone issue below. In the E9 runs (fresh seed each, backends on `:8022`–`:8024`, Vite on `:5185`, outside the timezone window) all 13 tests passed on desktop; the new E9 test skips itself on mobile. In the E10a run (fresh seed, backend on `:8025`, Vite on `:5185`, outside the timezone window) all 14 tests passed on desktop; the new E10a test skips itself on mobile.
- **Re-seed before every run** also because of the E7 cart test: it uses the demo shopper's account cart and expects it to start empty (the seed creates no cart), so a second run against the same database finds the previous run's lines and fails on the quantities. The E8a order test likewise expects the seeded litchi stock (4 → 2) and no earlier web orders; the E8b test expects the freshly seeded "Juice week" (it ends 7 days after seeding) and a `WELCOME50` not yet used; the E9 test expects the seeded `WEB-000002` still cancellable and the seeded review of `WEB-000001` approved. Since E9 the seed places two demo web orders for the shopper (`DemoAccountSeeder`; 2 mango juices in `WEB-000001`), so the receipt and POS tests expect juice stock 54, 150 and 148 (were 56, 152 and 150), and guest orders placed by the suite were `WEB-000003` onwards. Since E10a the seed places a third order, `WEB-000003` (1 kg Miniket Rice, shipped with Steadfast, in transit, COD unpaid; seeded Miniket Rice stock 321, juice still 54), so guest orders placed by the suite are `WEB-000004` onwards; the E10a test expects `WEB-000003` still in transit and no remittance yet (`REM-000001`).
- **Known issue — do not run the full-stack suite between 00:00 and 06:00 Asia/Dhaka** until it is fixed (pre-existing, not caused by E8b, E9 or E10a; still open after E10a). `config/app.php` has `timezone` hard-coded to `UTC`. In those hours the browser's local date is already the next day while the server's UTC date is not: the GRN form's invoice date (browser local date) fails "before or equal to today" on the server, and forcing the browser to UTC instead breaks the sales list's "today" filter, which uses the organization's timezone. The POS/back-office specs fail; the e-commerce specs are unaffected.
- The storefront runs on the Vite host (`localhost:5173`, listed in `SANCTUM_STATEFUL_DOMAINS`), so browser requests there are usually made stateful by Sanctum and `storefront.session` steps aside. The production path — a storefront host that is not stateful, with its own session, CSRF and 419 — is covered by the backend `CustomerSessionTest`.
