# Testing Guide

A module is not complete until its functionality and tests pass. Tests run against **PostgreSQL** (`pos_test`), never SQLite, because the system relies on PostgreSQL behaviour (row locks, partial indexes, `NUMERIC`, triggers).

## Backend (PHPUnit 12)

```powershell
cd backend
php artisan test                         # all suites
php artisan test --testsuite=Modules     # module tests only
php artisan test --filter=Checkout       # by name
php artisan test --parallel              # once suites grow
```

Suites (`phpunit.xml`):

| Suite | Location | Contents |
|-------|----------|----------|
| `Modules` | `app/Modules/*/Tests/**/*Test.php` | Module unit and feature tests (primary location) |
| `Unit` | `tests/Unit` | Cross-cutting unit tests |
| `Feature` | `tests/Feature` | Cross-module / end-to-end API flows |

Test environment: `DB_CONNECTION=pgsql`, `DB_DATABASE=pos_test`, array cache, sync queue, array mail. Credentials come from `backend/.env` (`DB_USERNAME`/`DB_PASSWORD`).

The array cache keeps PHP objects as they are, while every real store (file, database, Redis) serializes them — and `cache.serializable_classes` = `false` turns any object into an incomplete one on the way back. A cached Eloquent model therefore passes every array-store test and fails in production (E12a: the homepage and listings answered 500). Code that caches values needs a test on a serializing store: `StorefrontSeoTest::test_cached_reads_survive_a_serializing_cache_store` switches `cache.default` to a temporary file store and reads the cached endpoints twice (the second read comes from the cache).

PostgreSQL-only tests (`StockLockingTest`, since E8a `CheckoutConcurrencyTest` and since E8b `PromotionConcurrencyTest`: two real connections, committed data via `DatabaseTruncation`) skip themselves on other drivers — 4 skips on SQLite as of E10a (E9 and E10a add none, but their CHECK constraints and the E10a append-only triggers are PostgreSQL-only too), 5 since E12a (`StorefrontIndexesTest`: the partial storefront indexes exist; not run yet; E12b adds no skip, but its CHECKs and the jsonb Bangla-name search only behave like production on PostgreSQL); since X1 a sixth skip is the opt-in real PDF render (`ListExportTest::test_real_pdf_rendering_with_chrome`, `PDF_E2E=1`) — X1 run: 580 tests, 574 pass, 6 skipped; SC1 adds no skip (627 tests, 621 pass, 6 skipped), but its CHECKs and the partial unique index on `supplier_products` only behave like production on PostgreSQL; SC2 adds no skip either (658 tests, 652 pass, 6 skipped), but its CHECKs (statuses, limits, self-approval) and the append-only triggers on the procurement history tables and `rfq_awards` exist only on PostgreSQL (on SQLite the `AppendOnly` model trait still refuses changes); SC3 adds no skip either (681 tests, 675 pass, 6 skipped), but `stock_movements_value_only_check`, the landed cost CHECKs and the append-only triggers on `goods_receipt_charges` and `landed_cost_allocations` exist only on PostgreSQL; `CheckoutConcurrencyTest` and `PromotionConcurrencyTest` have not run yet because the local PostgreSQL run is still blocked. A quick interim run without PostgreSQL is possible with `DB_CONNECTION=sqlite DB_DATABASE=:memory: php artisan test`, but it does not satisfy the definition of done below: row locks, the ledger trigger and PostgreSQL error codes are only exercised on PostgreSQL.

### What each kind of test covers

| Kind | Example | Rules |
|------|---------|-------|
| Unit (domain) | `MoneyTest`, pricing calculator, tax-inclusive/exclusive math | No database, no framework boot. Golden values for every rounding rule. |
| Feature (API) | `POST /api/v1/pos/checkout` | `RefreshDatabase`; assert envelope, status, DB state, ledger rows. |
| Authorization | Cashier cannot adjust stock | One test per policy ability, both allow and deny. |
| Tenant isolation | User of branch A gets 404 for branch B sale | Required for every tenant-scoped resource. |
| Transaction | Payment failure rolls back sale and stock | Force a failure mid-transaction; assert nothing persisted. |
| Concurrency | Two checkouts for the last unit | Separate DB connections/processes; exactly one succeeds, stock never negative. |
| Idempotency | Same `Idempotency-Key` twice | One sale, identical responses; different payload → 409. |
