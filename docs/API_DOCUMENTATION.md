# API Documentation

- **Base URL:** `/api/v1`
- **Format:** JSON only (`Accept: application/json`)
- **Interactive OpenAPI docs:** `http://localhost:8000/docs/api` (generated by Scramble from code; JSON at `/docs/api.json`). Available in the `local` environment; exposing it elsewhere requires the `viewApiDocs` gate.

## Response envelope

Every response (except `204 No Content`) uses the same envelope.

**Success**
```json
{
  "success": true,
  "data": { "...": "..." },
  "meta": { "request_id": "01938c1e-…" }
}
```

**Paginated success**
```json
{
  "success": true,
  "data": [ { "...": "..." } ],
  "meta": {
    "request_id": "…",
    "pagination": { "current_page": 1, "per_page": 25, "total": 240, "last_page": 10 }
  }
}
```

**Error**
```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The given data was invalid.",
    "details": { "email": ["The email field is required."] }
  },
  "meta": { "request_id": "…" }
}
```

Clients should branch on `error.code`, not on `message`. Money values are serialized as **strings** with two decimals (`"125.50"`) — never parse them into binary floats for arithmetic.

## Cross-cutting headers

| Header | Direction | Purpose |
|--------|-----------|---------|
| `X-Request-Id` | both | Correlation id. Clients may send one (8–64 chars `[A-Za-z0-9-_.]`); the server always returns it. |
| `Idempotency-Key` | request | Required on `POST /pos/checkout`, `/returns`, `/returns/{id}/approve`, `/customer-payments`, `/expenses`, `/register-sessions/{id}/cash-movements`, the six web order steps `/web-orders/{id}/*`, the storefront's `POST /store/checkout`, (SC1/SC2) the purchasing transitions listed in [Supply chain](#supply-chain--purchase-requisitions-approvals-and-supplier-quotes-sc2) and (SC3) `POST /purchasing/landed-cost-vouchers/{id}/post`: 8–100 characters (`[A-Za-z0-9_\-:.]`), one per logical operation (the SPA uses a UUID); reuse it when retrying. Missing → `428 IDEMPOTENCY_KEY_REQUIRED`. A replayed response carries `Idempotent-Replayed: true`. Keys are scoped (ADR-014): staff `user:{id}`, signed-in shopper `customer:{account id}`, guest `cart:{cart token hash}`. |
| `X-Branch-Id` | request | Active branch. Optional; when sent it must be an active branch of the organization that the user is assigned to (or `branches.access_all`). Branch-scoped endpoints (Phase 4+) require it. |
| `X-Organization-Id` | request | Platform admins only: organization to act in. Ignored for tenant users. |
| `X-XSRF-TOKEN` | request | SPA cookie auth CSRF token (sent automatically by the frontend client). Also required on unsafe storefront requests that run the `storefront.session` stack (account, cart, wishlist). |
| `Retry-After`, `X-RateLimit-*` | response | Rate-limit information. |
| `Content-Language` | response | Storefront requests (E12b): `en` or `bn`, the language of the answer. The public API takes the language from `?lang=` only; storefront pages also from the `lang` cookie. |
| `Content-Disposition`, `X-Export-Rows` | response | List exports (X1): `attachment` with the file name; number of data rows in the file. |

## Conventions

- **Pagination:** `?page=1&per_page=25` (max 100).
- **Sorting:** `?sort=name` / `?sort=-created_at` (prefix `-` for descending); only whitelisted columns.
- **Filtering:** plain, validated query parameters per endpoint, e.g. `?status=active&role_id=…`; date ranges `?from=2026-10-01&to=2026-10-31` (inclusive).
- **Search:** `?search=term` (case-insensitive, whitelisted columns).
- **Rate limits:** 120 requests/minute per user (or IP when unauthenticated) on the `api` group; credential endpoints (`auth` limiter) 5/min per e-mail+IP and 20/min per IP; public storefront (`storefront` limiter) 300/min per IP; shopper credential endpoints (`customer-auth`) as `auth` (`POS_AUTH_RATE_LIMIT` per e-mail+IP, four times that per IP); shopper writes (`storefront-write`) 60/min per IP and 60/min per signed-in customer; checkout preview and placement (`checkout`) `POS_CHECKOUT_RATE_LIMIT` (default 10)/min per IP and shopper (customer account or guest cart); coupon attempts (`coupon`, `POST /store/cart/coupon`) `POS_COUPON_RATE_LIMIT` (default 10)/min per signed-in customer, else per guest cart, else per IP.
- **Identifiers:** UUIDv7 strings (device token ids are integers).
- **Versioning:** breaking changes go to `/api/v2`; additive changes stay in v1.

## Exports (X1)

Admin list endpoints answer `?export=xlsx|pdf|csv` (`csv` since Phase 7) with a file instead of the JSON page. The export is the list's own query: the same filters, `search` and `sort`, the same permission and tenant/branch scoping, **every matching row** (`page` and `per_page` are ignored).

```
GET /api/v1/sales?status=completed&from=2026-11-01&to=2026-11-05&sort=-sold_at&export=xlsx
→ 200  Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
       Content-Disposition: attachment; filename=sales-demo-mart-20261105-1430.xlsx
       Cache-Control: no-store, private
       X-Export-Rows: 42
```

| Rule | Value |
|------|-------|
| Formats | `xlsx` (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`), `pdf` (`application/pdf`), `csv` (`text/csv; charset=UTF-8`, Phase 7). Any other `export` value → 422 `VALIDATION_FAILED` on `export`. |
| File name | `<stem>-<organization slug>-<YYYYMMDD-HHmm>.<xlsx\|pdf\|csv>`, time in the organization's timezone (stems below). |
| Row limits | xlsx 50 000, csv 100 000, pdf 2 000 (`EXPORT_MAX_ROWS_XLSX`, `EXPORT_MAX_ROWS_CSV`, `EXPORT_MAX_ROWS_PDF`). Above → 422 `EXPORT_TOO_LARGE`, `details: {limit, rows, format}`; the rows are counted before any is read. |
| Rate limit | 10 exports per minute per user (`EXPORT_RATE_LIMIT`) across all lists → 429 `TOO_MANY_REQUESTS` with `Retry-After`. Counted before the row limit, so a refused export counts too. The JSON list is not affected. |
| PDF unavailable | 503 `PDF_UNAVAILABLE` when Chrome, Node or `backend/pdf-renderer/node_modules` is missing, or rendering fails or exceeds `PDF_TIMEOUT` (60 s). |
| Permission | The list's own permission (table below); nothing extra. 403 `FORBIDDEN` without it. Columns *Cost* (products), *Value* (stock) and *Unit cost* (stock movements) are included only with `products.view_cost`; `/inventory/valuation` requires it. |
| Audit | Each export writes `export.created` with `context: {list (stem), format, filters (query without export/page/per_page), rows}`. |
| Excel content | Sheet named after the title (≤ 31 characters); bold, frozen header row; money as numbers with format `#,##0.00`; numbers and quantities as numbers; dates and date-times as date cells in the organization's timezone; statuses as readable labels ("Partially received"); text never written as a formula. |
| PDF content | A4 (landscape above six columns): letterhead (name, legal name, address, phone, e-mail, tax number, storefront logo), title, filter summary ("Status: Completed · Branch: Dhaka Main · Date: 01 Nov–05 Nov 2026", or "All records"), generated-at in the organization's timezone and the user's name, table header repeated on each page, "Page X of Y". Embedded Poppins / Hind Siliguri, so Bangla text renders. |
| CSV content | UTF-8 with a byte-order mark, RFC 4180 (comma, CRLF line ends, a field quoted when it holds a comma, quote or line break; quotes doubled); one header row of the column labels, then the rows; money, numbers and quantities as plain decimal strings (`1234.50`, never grouped); dates `Y-m-d`, date-times `Y-m-d H:i` in the organization's timezone; statuses as labels. Formula-injection guard: a text cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'` (an exact decimal such as `-12.50` stays a number). No letterhead or filter summary. Streamed to a temporary file like xlsx. |

### E-commerce track — customer accounts, cart and wishlist (E7)

Shopper endpoints live under `/api/v1/store/*` like the rest of the storefront API (organization from the host, `throttle:storefront`). Accounts use their own session guard **`customer`** (ADR-002); a shopper session never satisfies `auth:sanctum`, and a staff session is never a shopper. Accounts resolve only inside the host's organization, so a session cookie of one store is anonymous on another store's host.

**Session and CSRF.** Storefront hosts are not in `SANCTUM_STATEFUL_DOMAINS`, so the `storefront.session` middleware gives the bootstrap, account, cart and wishlist routes the cookie stack Sanctum uses for first-party SPAs (encrypted cookies, session, `ValidateCsrfToken`; skipped when Sanctum already made the request stateful). `GET /store/bootstrap` and `GET /store/account/me` set the session and `XSRF-TOKEN` cookies; every POST/PUT/PATCH/DELETE must echo the cookie in `X-XSRF-TOKEN` (missing or stale → `419 CSRF_TOKEN_MISMATCH`). The storefront client then fetches `GET /store/account/me` once and retries the request once. Catalog, CMS and geography routes stay sessionless.

**Signed-in routes** (marked *C*) need `auth:customer`; they answer `401 UNAUTHENTICATED` without a shopper, and also when staff disabled the account or the customer record was archived or deactivated since sign-in (the shopper is signed out on that request). Routes marked *P/C* work for guests and shoppers.

**Cart pricing.** Nothing about prices is stored. `CartPricer` asks the OnlineCatalog contract (`StorefrontCatalog::variantsForCart`) for every line's live data — listing state, current selling price, compare-at price, availability and on-hand quantity at the fulfilment store, unit, tax rate — and totals the countable lines with the POS `SaleCalculator` in the organization's tax mode and currency, so the cart shows exactly what the server computes (ADR-005). Per line:

- `purchasable` — the listing is live, the product active and not archived, the variant active. `false` → `issues` gets `unavailable`.
- `in_stock` — the product does not track stock, or the fulfilment store has some (no fulfilment store = nothing on hand). `false` on a purchasable line → `out_of_stock`.
- `max_quantity` — on-hand quantity (`"5.000"`) for stock-tracked products, `null` when stock is not tracked. A quantity above it sets `exceeds_stock` (and `issues` `exceeds_stock`); the line counts with `max_quantity`.
- Lines that are not purchasable or out of stock stay in the cart, keep their quantity and show `line_total: "0.00"`; they are left out of `subtotal`, `tax_total` and `total`. Quantities are never changed on read — the shopper fixes them.
- `line_total` = countable quantity × unit price (before tax), so the lines add up to `subtotal`. In exclusive mode `total` = `subtotal` + `tax_total`; in inclusive mode (`prices_include_tax: true`) the tax is contained in the prices and `total` = `subtotal`.
- `item_count` — sum of the quantities of purchasable lines as entered (trailing zeros dropped: `"3"`, `"1.5"`); `quantity` is shown the same way. `product.url` is `null` (and `product.name` "Product no longer available") when the product has no listing any more.
- An empty or missing cart → `id: null`, `items: []`, zero totals.

**Merge on sign-in.** Login, registration and password reset move the guest cart of the request's cookie into the shopper's cart inside one transaction: quantities of the same variant are summed and capped at the on-hand quantity (when tracked and above zero) and at 999; guest lines that would exceed the 50-line limit are dropped. Every capped or dropped line counts in `merge.capped_lines`; `merged_lines` counts the lines added or increased. The guest cart is deleted and the cookie forgotten. Without a guest cart `merge` is `{merged_lines: 0, capped_lines: 0}`. Customer carts never expire; guest carts are deleted 30 days after their last change (`cart:prune`, daily).

**Catalog additions.** Product cards add `default_variant_id` (the only active variant of a single-variant product, else `null` — used by the card's *Add to cart*); `GET /store/products/{slug}` adds `allow_decimal` (the product's unit allows quantities with up to 3 decimals).

Pages: the shell answers `/account`, `/account/login`, `/account/register`, `/account/forgot-password`, `/account/reset-password`, `/account/verify-email`, `/account/profile`, `/account/addresses`, `/cart` and `/wishlist` with `noindex` and the title "My account", "Cart" or "Wishlist" `| {store}`.

**Placement body.**

```json
{
  "contact": { "name": "≤ 120", "email": "≤ 255", "phone": "Bangladeshi mobile" },

  "payment_method": "cod | bank_transfer",
  "notes": "≤ 500, optional",

```

- `address` is required unless a signed-in customer sends `shipping_address_id` (one of their own addresses, else a field error); the district must be in the division (field error on `address.district_id`). Phones are normalized to `01XXXXXXXXX`.
- `save_address: true` (customers with an inline address) adds it to the address book after the order is placed — skipped silently when `area` is empty (the book requires it) or the book is full; the order never fails because of it.
- `expected_total` is the total the shopper saw. The server reprices everything (cart lines through `CartPricer`, delivery fee, COD fee); a different total → `409 TOTAL_CHANGED` with `details.preview`, and nothing is placed.
- Delivery: the method's `fee`, or `"0.00"` once the goods total after tax reaches `free_over`. COD fee: the method's `cod_fee` when paying cash on delivery. Neither is taxed in E8a. `total` = cart total + delivery + COD fee.
- Check order (first failure wins): field validation (`VALIDATION_FAILED`), `GUEST_CHECKOUT_DISABLED`, `CHECKOUT_UNAVAILABLE`, `CART_EMPTY`, `CART_HAS_ISSUES`, saved-address / district-in-division field errors, `SHIPPING_UNAVAILABLE`, `PAYMENT_METHOD_UNAVAILABLE`, `TOTAL_CHANGED`, `INSUFFICIENT_STOCK`. Before the controller: `428 IDEMPOTENCY_KEY_REQUIRED`, `422 CART_EMPTY` for a guest without a cart cookie (no idempotency scope), `409 IDEMPOTENCY_KEY_REUSED` / `IDEMPOTENCY_REQUEST_IN_PROGRESS`, `429`.
- **Idempotency.** One key per attempt. A retry with the same key and body returns the stored 201 (`Idempotent-Replayed: true`) — also for a guest whose cart has meanwhile been converted, because the scope is the cart cookie's token hash. Failed attempts release the key.
- Result: cash on delivery → `status: confirmed`; bank transfer → `status: pending_payment` with `expires_at` = placed + the method's `hold_hours` (default 48). `payment_status: unpaid`. Unverified shopper e-mail addresses may check out.

### E-commerce track — promotions, coupons, flash sales and hot deals (E8b)

Promotions apply to the **online store only** (the POS ignores them). Everything is computed on the server: the shopper never sends a discount, only a coupon code. A promotion is **live** when it is active and inside its schedule (`starts_at` ≤ now < `ends_at`, either end optional).

**Application rule** (`PromotionEngine`, the same for the cart, the checkout preview, placement and product display):

1. **Product level** (scope `products`, `categories` — sub-categories included — or `brands`): each counted line gets **at most one** product promotion — among the live automatic ones and the coupon's, the one giving that line the largest discount; ties → earliest `ends_at`, then smallest id. `percent` = line amount × value %; `fixed` = value × quantity (per unit), never more than the line amount. `min_subtotal` is compared with the subtotal of all the lines the promotion matches, before discounts. `max_discount` caps the promotion's total over its lines; the cap is shared out in proportion to the uncapped amounts.
2. **Order level** (scope `order`, `percent`/`fixed`): the **single best** live automatic order promotion or the coupon's applies to the subtotal after product discounts; its `min_subtotal` is compared with the subtotal **before** any discount; `max_discount` caps a percentage. It is allocated over the lines as `SaleCalculator`'s invoice discount.
3. **Free delivery** (`free_shipping`, order scope only): when any live automatic free-shipping promotion or the coupon's is eligible (`min_subtotal` on the subtotal before discounts), the delivery fee is waived — the COD fee is still charged. An automatic one is preferred over the coupon's.
4. **Tax** is computed by `SaleCalculator` after the discounts (both tax modes).
5. A valid coupon whose promotion ends up unused because an automatic offer gives more stays on the cart with `applied: false`, `reason: "better_offer"`, `message: "A better offer is already applied."`, and is not redeemed.

There are no customer groups, stacking flags or priorities. Usage limits: `usage_limit` counts placed orders that used the promotion; `usage_limit_per_customer` counts them per customer record for signed-in shoppers and per lower-case contact e-mail for guests (known only at checkout); a coupon's own `usage_limit` counts its `used_count`. Automatic promotions whose limit the shopper has reached are skipped silently.

`COUPON_INVALID` reasons (`details.reason`; `error.message` is the shopper-facing text, also returned as `coupon.message` when a stored coupon becomes invalid):

| Reason | Message | When |
|--------|---------|------|
| `not_found` | This coupon code is not valid. | Unknown code, malformed code, code or promotion switched off, or a code of an automatic promotion — one generic answer. |
| `not_started` | This coupon is not valid yet. | Before the promotion's `starts_at`. |
| `expired` | This coupon has expired. | At or after `ends_at`. |
| `usage_limit_reached` | This coupon has already been used up. | The code's `usage_limit` or the promotion's `usage_limit` is reached. |
| `customer_limit_reached` | You have already used this coupon. | `usage_limit_per_customer` reached — checked when applying only for signed-in customers; guests are counted by e-mail at checkout. |
| `min_subtotal` | Add products worth at least {min_subtotal} {currency} to use this coupon. | The relevant subtotal (whole cart for order scope, matching lines for product scopes) is below `min_subtotal`; `details.min_subtotal`. |
| `not_applicable` | This coupon does not apply to the products in your cart. | No line matches the promotion's targets; also an empty cart. |
| `better_offer` (never an error) | A better offer is already applied. | Valid, but an automatic promotion gives more. |

A coupon that becomes invalid after it was applied (cart changed, schedule over, limit reached) **stays on the cart** with `applied: false` and its `reason`/`message`, is ignored in the totals, and never blocks checkout: the order is placed without it (the preview shows why). Only `DELETE /store/cart/coupon` or another code removes it.

**Cart fields** (added to the E7 shape):

- Lines: `discount_amount` — the line's product discount plus its share of the order discount (as `SaleCalculator` allocates it; `"0.00"` for flagged lines); `promotion` — `{id, name}` of the product promotion on that line, or `null`. `line_total` stays quantity × unit price.
- Totals: `subtotal` (before discounts), `discount_total` (product + order discounts), `tax_total` (after discounts), `total`.
- `promotions: [{id, name, kind: "product" | "order", amount}]` — the product promotions used, then the order promotion; `free_shipping: null | {id, name}` — the free-delivery promotion that will waive the delivery fee at checkout; `coupon: null | {code, applied, reason, message, promotion_name}` (`reason`/`message` `null` when applied; `promotion_name` `null` for an unknown code).

**Checkout and order fields:** `discount_total` (goods discounts), `shipping_discount` (the delivery fee waived by free delivery; `shipping_total` is then `"0.00"`; the COD fee is unchanged), `promotions: [{name, kind: "product" | "order" | "shipping", amount}]` (shipping only when a fee was actually waived — a method that is already free by its `free_over` waives nothing), `coupon_code` (only when the coupon was redeemed, else `null`), `lines[].discount_amount`. `total` = cart total (after discounts and tax) + delivery after the waiver + COD fee. The confirmation e-mail lists the discounts, the coupon and the free-delivery saving.

**Placement** (inside the E8a transaction, after the cart lock and the first repricing): the promotions the order would use **that have a usage limit** and the coupon are locked (`FOR UPDATE`, sorted by id) and the cart is priced again under the locks (at most three rounds, in case the new pricing picks another limited promotion). A limit reached meanwhile drops that promotion; the new total then differs from `expected_total` → `409 TOTAL_CHANGED` with the fresh preview, whose `coupon.reason` explains it. Then `order_promotions` gets one snapshot row and `promotion_redemptions` one row per promotion used (`coupons.used_count` + 1 for a redeemed code). An idempotent replay returns the stored response and redeems nothing. Cancelling or expiring the order does **not** free the redemption (E10 may revisit). Unlimited promotions are not locked.

**Catalog display.** Cards (listing, search, related, homepage sections, wishlist) add `promotion: null | {id, name, type, value, ends_at, show_countdown, price}`: the best live **automatic product-scope** promotion for **one unit** of the variant giving the card's `price` (`price` = promotional unit price; `type`/`value` let the client format "−10 %" or "−৳20"). Promotions whose total `usage_limit` is reached are not shown; per-customer limits are not known there; coupon promotions are never shown; a product promotion whose `min_subtotal` is above the unit price does not show on cards. `GET /store/products/{slug}` adds `promotion` (same shape, for the product's `price`) and `variants[].promo_price` (`null` when no promotion applies). **Filters and sorting keep the base price** (`price_min`/`price_max` and the price sorts); `compare_at_price`, `on_sale` and `discount_percent` are unchanged (the storefront shows the promotion badge instead of the "Sale" badge when both exist).

**Hot deals section** (`hot_deals`; staff `GET /storefront/homepage-sections/types` lists it): config `{promotion_id: uuid | null (null = every live flash sale), limit 4–12 (8), view_all_url: site path or http(s) | null}`. `promotion_id` must be an automatic promotion with `show_countdown` (`PROMOTION_NOT_FOUND`). The coupon's `min_subtotal` (500) is compared with the subtotal before discounts (500.00), and its 50 off applies after the product discount (450.00 → 400.00); 15 % VAT on 400.00 makes the goods total 460.00 (with a 60.00 home delivery, the placed order's `total` is 520.00). With 19 juices the answer would be `422` with `error.code` `COUPON_INVALID`, `details: {reason: "min_subtotal", code: "WELCOME50", min_subtotal: "500.00"}`. Placing the order gives `discount_total: "100.00"`, `coupon_code: "WELCOME50"` and `promotions: [{name: "Juice week", kind: "product", amount: "50.00"}, {name: "Welcome 50", kind: "order", amount: "50.00"}]`.

### E-commerce track — SEO and performance (E12a)

Crawler files are served by Laravel on the storefront host (outside `/api/v1`); they start no session and set no cookie (`throttle:storefront`). "Indexable" below means: the storefront is open (not a staff preview), `allow_indexing` is true and the request's host is the primary domain.

| GET `/sitemaps/{name}.xml` | `pages`: `/`, `/shop`, `/blog` (no lastmod) and visible content pages `/pages/{slug}`. `products-{n}`: live products by slug (published listing within its window, active product, at least one active variant) `/product/{slug}` with `<lastmod>` = the later of listing and product `updated_at` and `<image:image><image:loc>` (first image, absolute). `categories` / `brands`: visible listings `/category/{slug}`, `/brand/{slug}`. `blog`: blog categories with at least one readable post `/blog/category/{slug}` and readable posts `/blog/{slug}`. Semantics (`Shared\Application\Support\TranslationInput`):
- `translations` left out → kept. `translations: null` or `{"bn": null}` → all removed.
- Partial merge: a sent field replaces its translation; a blank one (`""`, whitespace, `null`) removes it; fields not sent are kept. Values are trimmed.
- Exceptions: menu items (`PUT …/items` replaces the whole tree) and the announcement (`PUT /storefront/theme` replaces the whole document) store exactly what is sent — no merge. The theme returns `announcement.translations` as stored (`null` or `{"bn": {"text": …}}`).
- Errors (422 `VALIDATION_FAILED`, in `error.details`): `translations.bn.<field>` — too long or not a string; `translations.bn` — unknown field (e.g. `slug`); `translations` — unknown locale (e.g. `fr`) or not an object. Menu items use `items.{i}.translations…` (and nested `children` paths), the announcement `announcement.translations…`.
- Audit snapshots of listings, pages, FAQ, posts and sections record a `translations_hash` (xxh128 of the document), not the texts.

**Public reads.** Each translatable field reads its Bangla value when non-blank, else the base value — per field (`Shared\Domain\Translations::pick`), so a half-translated record mixes Bangla and English. Slugs and URLs are never translated. Localized: `/store/products` cards (name, short description, category and brand names) and facets, `/store/products/{slug}` (name, texts, `seo.*`, breadcrumbs incl. "হোম"), related products, `/store/search/suggest`, `/store/categories[/{slug}]`, `/store/brands[/{slug}]`, `/store/homepage` (section title / subtitle / config texts, banners, catalog sections), `/store/bootstrap`, `/store/pages/{slug}`, `/store/faq`, `/store/blog*`, `/store/shipping-methods`, checkout preview, payment methods and cart line names, the order page's `payment_method_label` and `payment_instructions`, review product names. SEO stays per field: `seo.title` = Bangla SEO title, else base SEO title, else the localized name.
- **Search** (`q` on `/store/products`, `/store/search/suggest`) matches base **and** Bangla names (products, brands, category suggestions) in either language (`lower(translations->'bn'->>'name') LIKE …`; verified on PostgreSQL 18, 2026-11-11).
- **Geography:** `GET /store/geo/divisions` · `/store/geo/districts` with `?lang=bn` → `name` is the Bangla name, rows sorted by it; `name_bn` unchanged. Staff `/geography/*` stay English.
- **Not translated:** attribute names and values, variant option names, product page tab labels, features-strip / testimonials items, FAQ group names, store name and meta description, order line snapshots.

**Orders and accounts.** Checkout placement (`POST /store/checkout?lang=bn`) stores `orders.locale` = the request's language; the shopper's order (`GET /store/orders/{number}`, account order detail) returns `locale` (`en|bn`). Snapshots (product, delivery method, promotion, place names) are taken in English whatever the language. Sign-up, sign-in and password reset set `customer_accounts.preferred_locale` from `lang`; the account profile returns `preferred_locale` (`null` until the first sign-in after E12b). | `min_order_qty` | Optional, > 0, up to 3 decimals, or `null`. |
| `lead_time_days` | Optional integer 0–365; `null` = 7. |
| `supplier_sku` | Optional, ≤ 64 characters (trimmed; blank = `null`). |
| `is_preferred` | Optional boolean. `true` unsets the variant's other preferred row; refused on `is_preferred` for an inactive row or an inactive / archived supplier. |

Whole-unit products (unit without decimals) need whole `pack_size` and `min_order_qty` ("… is bought in whole units (pcs).").

**Reorder rules.** `PUT {store_id, rules: [{variant_id, min_qty, max_qty?, is_active?}]}` — 1–500 rules, `variant_id` distinct. `min_qty` (reorder point) ≥ 0; `max_qty` (order-up-to level) ≥ `min_qty` or `null` (= cover `coverage_days` of sales); up to 3 decimals, whole for whole-unit products; `is_active` defaults to `true`; an omitted `max_qty` is saved as `null`. Errors (422 `VALIDATION_FAILED`, nothing saved): `store_id` not accessible or inactive; `rules.N.variant_id` unknown or not stock-tracked; `rules.N.max_qty` "The maximum must be at least the minimum."; fractional quantities of whole-unit products. Row: `{id, store: {id, code, name, branch_id, branch_name}, variant: {id, product_id, product_name, variant_name, sku, unit_code, track_batches, allow_decimal}, min_qty, max_qty, is_active, updated_at}`. Without an active rule a store uses the variant's `reorder_level` as `min_qty` and no maximum.

`meta`: `pagination`, `store` `{id, code, name, branch_id, branch_name}`, `source_store` (same shape; `null` when none is set, it is this store, or it is inactive) and `settings` `{coverage_days, velocity_days, safety_days}`. Rows are ordered by product name, variant name and SKU. `supplier` is `null` when the variant has no usable preferred supplier (an active preferred row of an active, non-archived supplier); the purchase is still suggested (pack 1, lead 7) and the admin flags it. `unit_cost` = the preferred catalog cost, else the unit cost of the variant's most recent goods receipt line (any supplier), else the variant's purchase price. `lead_time_days` = the preferred row's lead time, else 7. `pack_size` / `min_order_qty` come from the preferred row (`1.000` / `null` without one); `min_qty`, `max_qty`, `has_rule` show the effective rule. `draft_on_order` = outstanding quantity on the store's **draft** purchase orders — shown as a warning, not counted as available.

Calculation (`Purchasing\Domain\Reorder\ReorderCalculator`, pure — no database, no clock; inputs gathered by `Purchasing\Application\Queries\ReorderSuggestions`):

| Value | As implemented |
|-------|----------------|
| Candidates | Variants with an active rule in the store, a `reorder_level` > 0, sales in the window, or negative stock — then only stock-tracked, sellable variants. |
| `on_hand` | Σ `stock_levels.quantity` of the store (all batches). |
| `on_order` | Σ (`quantity − received_quantity`) of the store's purchase order lines in status `ordered` or `partially_received` (drafts excluded). |
| `in_transit` | Σ line quantities of `in_transit` transfers into the store. |
| `sold` | Net units sold at the store since now − `velocity_days` (a rolling window): −Σ signed `stock_movements.quantity` of types `sale`, `online_order`, `sale_cancellation`, `online_order_cancel`, `sale_return`, `online_return`; never below 0. Web orders count at their fulfilment store. |
| `avg_daily` | `sold / velocity_days` (3 dp). |
| `min_qty`, `max_qty` | The store's active rule, else `reorder_level` and `null`. |
| `reorder_point` | `max(min_qty, ceil(sold × (lead_time_days + safety_days) / velocity_days))` — the velocity part is rounded up to whole units for every product (2.4 kg → 3). |
| `target` | `max_qty` when set, else `reorder_point + ceil(sold × coverage_days / velocity_days)`. |
| `available` | `on_hand + on_order + in_transit`. A row is returned only when `available ≤ reorder_point` and `need = target − available` > 0 (whole-unit products: `need` rounded up). |
| `suggested_transfer` | When a source store is set, active and not this store: `min(need, surplus)` with `surplus = max(0, source on_hand − source reorder_point)` (the source's own rule or reorder level and sales, the same lead and safety days); whole-unit products round both down. Otherwise 0. |
| `suggested_purchase` | `need − suggested_transfer`, when > 0: raised to `min_order_qty`, then rounded up to whole multiples of `pack_size`; whole-unit products whole. |
| `reason` | `below_min` when `available ≤ min_qty`, else `velocity`. |
| `days_of_cover` | `on_hand × velocity_days / sold` (1 dp, ≥ 0); `null` when nothing was sold. |

### Supply chain — purchase requisitions, approvals and supplier quotes (SC2)

Slice 2 of the supply chain track. Money is a 2-decimal string, unit costs / quoted prices 4, quantities 3. Requisitions and RFQs belong to a store and its branch: lists are limited to the user's branches, another branch's or organization's document answers 404, a store outside the user's branches answers 422 `VALIDATION_FAILED` on `store_id`. Every status transition takes an `Idempotency-Key` (428 `IDEMPOTENCY_KEY_REQUIRED` without; a retry with the same key and body replays the first answer). Transitions run in one transaction under the document's row lock, are audited and append a status history row; a step not allowed from the current status answers 422 `INVALID_STATUS_CHANGE` (`details.from`, `to` where given).

**Approval rules** (`Purchasing\Domain\Procurement\ApprovalPolicy`, pure; amount = requisition estimate or order total incl. tax, base currency):

| Amount | Level | Who may approve |
|--------|-------|-----------------|
| ≤ `auto_approve_limit` (default 10 000.00) | `none` | Nobody: a requisition is approved on submit (`approved_by` null, `auto_approved: true`, history note "Approved automatically…", no notification); an order is placed on submit. |

- Boundaries belong to the lower tier (10 000.00 → `none`, 10 000.01 → `manager`; equal limits skip the manager tier).

- The level is fixed when the document is submitted; later limit changes apply to documents submitted afterwards.
- Purchase orders need no approval when `require_po_approval` is false, the total is ≤ the auto limit, or the order is **pre-approved** (created from an approved requisition, directly or through an RFQ award) and its total ≤ `round(approved_amount × 1.05, 2)` (`pre_approval_limit`). ### Supply chain — landed cost and supplier performance (SC3)

**Receipt charges** — `POST /purchasing/receipts` with `charges` (optional, ≤ 20):

```json

             {"type": "handling", "description": "Packing and loading", "amount": "150.00", "allocation": "quantity"}]}
```

- `type` `freight|duty|insurance|handling|other`; `description` ≤ 120; `amount` > 0 and `tax_amount` ≥ 0 (default 0), up to 2 decimals; `allocation` `value` (by line subtotal, before tax) or `quantity` (by base quantity); `charge_supplier_id` — who bills the charge: empty = on this receipt's invoice, else an active, non-archived supplier (422 on `charges.N.charge_supplier_id`).
- **Allocation:** each charge separately, largest remainder (`Money::allocate`; leftover cents to the largest remainders, ties to the earlier line), so a charge's parts add up exactly; a `value` charge over lines that are all worth 0 is spread by quantity. Line `landed_cost` = Σ its parts; `landed_unit_cost` = round(unit_cost + landed_cost ÷ quantity, 4). The stock movement of the line is posted at `landed_unit_cost` (equal to `unit_cost` without charges), so the weighted average and the batch level include the charges.
- **Totals:** `subtotal` / `tax_total` / `total` stay the goods; `charges_total` = Σ amounts (capitalised), `charges_tax_total` = Σ tax (recoverable, not capitalised), `landed_total` = subtotal + charges_total, `payable_total` = total + amount and tax of the charges without a charge supplier — what the main supplier is owed for this invoice. Charges with a charge supplier are owed to that supplier (amount + tax).

**Posting** — `POST /purchasing/landed-cost-vouchers/{id}/post` with `Idempotency-Key`, one transaction:

1. Lock the voucher; anything but a draft → `INVALID_STATUS_CHANGE`. The charge supplier must still be active.
2. Spread every charge over all lines of the voucher's receipts (receipts in voucher order, then line id; same allocator as receipt charges).
3. **On hand per line** (Inventory `StockValuation::onHandFromDocument`, levels locked `FOR UPDATE` in `store|variant|batch` order): on hand from the receipt on its level = clamp(level quantity now − quantity posted into the level by other documents after the receipt's movement, 0, quantity the receipt brought), capped by the line's received − returned quantity; several lines of one receipt on the same level take it last line first. The ledger pools units per level, so this assumes the newest stock is still on hand (first in, first out); it is exact for batch-tracked lines whose batch nothing else fills. Products that do not track stock have nothing on hand.
4. Split each line's amount exactly (largest remainder) into `on_hand_amount` (amount × on hand ÷ received) and `consumed_amount` (the rest).
5. On-hand shares summed per level → one movement per level, type `landed_cost`, quantity 0, `value` = the share, `unit_cost` = the per-unit increase, `balance_after` = the unchanged quantity, reference `landed_cost_voucher` / the voucher number; the level's average becomes (quantity × average + value) ÷ quantity (4 dp).
6. Consumed shares summed → one expense `EXP-…` in the category "Landed cost on sold stock" (created on first use), dated the voucher date, reference the voucher number, party the charge supplier, `on_account: true` (no payments-ledger entry, `method` `bank_transfer`, `method_label` "On supplier account", not voidable: `EXPENSE_ON_ACCOUNT`).
7. Append-only `landed_cost_allocations` rows per receipt line; totals, `expense`, `posted_by` / `posted_at`; audited `landed_cost_voucher.posted`.

The voucher `total` (with tax) is then owed to the charge supplier: statement entry `landed_cost_voucher` (date = voucher date, reference = the voucher's reference or "Landed cost"), included in `/purchasing/supplier-balances` and settled by supplier payments.

**Supplier payables (SC3).** Balance = opening balance + Σ receipts' `payable_total` + Σ receipt charges the supplier billed (amount + tax; statement entry `receipt_charge`, `id` / `number` = the receipt's, reference "Charge on GRN-…: Freight — {description}", date = the receipt's invoice date) + Σ posted vouchers it billed − Σ purchase returns − Σ payments. Payments are on account. Purchase returns still credit the supplier's unit cost (not the landed cost).

| `on_time_rate` | Of those orders with an `expected_date` and at least one receipt: % whose delivery date ≤ `expected_date`. Delivery date = the invoice date of the receipt that completed the order when it is fully received, else the first receipt's. `on_time_orders` = the orders counted. |
| `fill_rate` | Σ received ÷ Σ ordered (base quantities; received capped per line at the ordered quantity) over those orders that are `received`, still `ordered` / `partially_received` past their expected date, or cancelled after a partial receipt. |
| `avg_lead_days` | Mean days from order date to the first receipt (orders with a receipt), 1 decimal. |
| `return_rate` | Σ returned ÷ Σ received quantity on its receipt lines with invoice date in range. |
| `price_change_pct` | Per variant: average unit price (Σ line subtotal ÷ Σ quantity, the supplier's price before charges and tax) in range vs the previous period, as a % change; weighted by the variant's line subtotal in range. Null without a variant bought in both periods. |
| `quote_response_rate` | RFQ invitations sent to it in range (`rfq_suppliers.sent_at`, converted to the organization's date) that have a recorded quote (received or declined) ÷ invitations. `quote_invitations`, `quote_responses` = the counts. |
| `quotes_won` | RFQ award rows for it in range (`rfq_awards.created_at`, organization date). |
| `late_deliveries`, `short_deliveries` | Orders in range delivered after the expected date or still undelivered past it (not cancelled); fill-eligible orders received short. |
| `score` | Below; integer 0–100 as a string, null when no component has data. |

Rates are percentages with 2 decimals; null when there is nothing to measure.

**Score** (`Purchasing\Domain\Performance\SupplierScore`, pure): components 0–100 (clamped) and weights —

| Component | Weight | Value |
|-----------|--------|-------|
| `on_time` | 35 | `on_time_rate` |
| `fill` | 30 | `fill_rate` |
| `returns` | 15 | 100 − 5 × `return_rate` (20 % returned → 0) |
| `price_stability` | 10 | 100 − 5 × max(0, `price_change_pct`) (decreases count as stable; +20 % → 0) |
| `responsiveness` | 10 | `quote_response_rate` |

score = round(Σ weight × component ÷ Σ weight of the components present). A component without data is left out and the others are scaled up to 100 (`score_weights` lists the weights used); none → null.

**Rows and meta:**
- Rows carry the column keys plus ids for links (`product_id`, `branch_id`, `group_id`, …). Without `products.view_cost`, the cost-sensitive keys are removed from rows and totals and listed in `meta.omitted_columns`.
- `meta.columns` are the columns this user gets for this run. A grouped report relabels its `group` column, e.g. "Category".
- `totals` cover every row of the run, not only the page. It is `null` for statements.

**Rules:**
- **Dates:** `date_from` and `date_to` are required on time-based reports and are organization days, both inclusive. `date_to < date_from` → 422 on `date_to`.
- **Range:** at most **366 days** for daily rows (`granularity` `day`, or `group_by=day`), otherwise **1 827 days (five years)**. A longer range → 422 `RANGE_TOO_LARGE`, `details: {max_days, days}`. `max_range_days` in the definition gives the limit.
- **Branch scope:** the branches read are the user's accessible branches ∩ `branch_id`, never the client's word alone. A branch of another organization → 422 "does not exist". An inaccessible branch → 422 on `branch_id`. A store outside the scope → 422 on `store_id`. A `category_id` includes its sub-categories.
- **Sort:** `sort=<column>` or `-<column>` must name a sortable column this user can see; otherwise 422 on `sort`. The default is the definition's `default_sort`. When that default is a cost column the user may not see, the first visible sortable column is used ascending. Ties keep the report's own order, and numbers compare exactly. Statements (`default_sort: null`) ignore `sort`.
- **Paging:** `page` (default 1) and `per_page` (default 50, at most 500). Reports with `paginated: false` return every row on one page.
- **Organization timezone:** `meta.params.timezone`; the currency is the organization's base currency.

**Sales definitions** (`SalesFacts`, shared by every sales report, `profit_and_loss`, `tax` and the dashboard):

| Figure | Definition |
|--------|-----------|
| POS | Lines of **completed** sales by `sold_at`, minus lines of **completed** sale returns by the return's `decided_at`. Cancelled sales count nowhere (see `sales_by_cashier.cancelled`). |

```json
  "sales_by_branch": null},
 "meta": {"params": {"date_from": "2026-10-09", "date_to": "2026-11-07", "branch_id": null, "previous_from": "2026-09-09",
                     "previous_to": "2026-10-08", "today": "2026-11-07", "timezone": "Asia/Dhaka", "currency": "BDT"},
          "generated_at": "…", "omitted": [], "cache_seconds": 60}}
```

**KPIs:**
- Each KPI is `{value, previous, change, change_pct}`; `change_pct` is `null` when the previous value is 0.
- `total_sales` = net sales of the range (shown as *Net sales*).
- `today_revenue` = today's net sales against yesterday's.
- `orders_count` = POS sales + delivered web orders.
- `gross_profit` is `null` and listed in `meta.omitted` without `products.view_cost`.
- `average_ticket` = net sales ÷ orders.
- `returns_amount` = returns excluding tax.

**Lists:**
- `sales_trend` has one point per day of the range, zeros included. `gross_profit` appears only with cost access.
- `top_products`: 10 by net sales, then quantity.
- `low_stock`: the `low_stock` rule; `count` plus the 10 with the largest shortfall.
- `recent_transactions`: the 10 latest of POS sales (any status, by `sold_at`) and web orders (any status, by `placed_at`; only with `web_orders.view`). `link` is the admin path.
- `sales_by_branch`: one row per branch in scope (`{branch_id, name, net_sales, orders}`), or `null` when the scope has one branch.

**Cache:** 60 s, keyed by organization × the sorted list of branches the query reads × range × today × cost access × web-order access. A user with different branch access never gets another user's cached figures. The TTL is short and does not depend on any data version.

**Exports:** `GET /reports/{key}?…&export=xlsx|csv|pdf` uses the X1 exporter (§ Exports):
- the same permission, parameters, branch scope and sort as the JSON run;
- **every row** (`page` / `per_page` ignored), plus a last row *Total* when the report has totals;
- cost-sensitive columns are left out without `products.view_cost`;
- stem `report-<key with hyphens>` (`report-sales-by-product-demo-mart-20261107-1430.csv`), title = the report title;
- filter summary from the resolved parameters ("Period: 01 Nov–07 Nov 2026 · Branch: Dhaka Main · Group by: Category", "As of: …" for reports without a range, "Branches: your branches" for a branch-limited user);
- `stock_movements` streams from SQL in chunks; the others are aggregated first;
- row limits, throttle, audit (`export.created`, list = the stem) and errors as for lists;
- column types map money → money, quantity → quantity, number and percent → number, date and datetime → date cells.

**Errors:** `RANGE_TOO_LARGE` (422) is new. Parameter, sort and branch errors are `VALIDATION_FAILED` on the field. New permissions: `reports.view`, `reports.financial`, `dashboard.view`.

**Ask** — `POST /ai/ask`:

```json
{"question": "Which products sold best this month?", "branch_id": "…",
 "history": [{"role": "user", "content": "…"}, {"role": "assistant", "content": "…"}]}
```

- `question`: string, 2–1000 chars. `branch_id`: optional uuid of an accessible branch, the default branch of the question.
- `history`: optional, ≤ 6 turns `{role: user|assistant, content ≤ 4000 chars}`, alternating, starting with `user` and ending with `assistant` (otherwise 422 on `history`). Nothing is stored on the server.

```json
{"data": {
  "answer": "**Net sales this month (1–7 Nov 2026, all branches): ৳45,426.50.** …",
  "report": {"key": "sales_by_product", "title": "Sales by product",

             "columns": [{"key": "product", "label": "Product", "type": "text", "cost_sensitive": false, "sortable": true}, "…"],
             "rows": [{"product_id": "…", "product": "Butter Cookies 200g", "net_sales": "3320.00", "…": "…"}],
             "totals": {"net_sales": "…"}, "total_rows": 4, "omitted_columns": [],
             "link": "/reports/sales_by_product?date_from=2026-11-01&date_to=2026-11-07&channel=all&sort=-net_sales"},
  "tools_used": [{"name": "sales_by_product", "params": {"date_from": "2026-11-01", "date_to": "2026-11-07", "sort": "-net_sales"}, "ok": true}],

```

- `answer`: Markdown (no HTML), in the language of the question (English or Bangla).
- `report`: the last registry report a tool ran, as the user may see it: ≤ 50 rows, names kept, cost columns per `products.view_cost`, `link` = the admin reports URL with the resolved parameters. `null` when no report ran, the question is unsupported or the model refused.

**Explain reorder** — `POST /ai/explain-reorder {"store_id": "…"}` (uuid of an active store of an accessible branch; AI is checked before the store):

```json
{"data": {"narrative": "12 items need attention in Main Store: 3 to buy, …", "status": "ok",
```

  - flash_sale_bar `{promotion {id, name, ends_at, state}, products: [card], claimed: null|{used, limit}}` — `claimed` only when the promotion has a usage limit (real redemptions, capped). `promotion_id: null` = the active countdown promotion that ends soonest; published only while active with an end date
  - bundle `{products: {<id>: product detail}}`; published `props.items` are filtered to available products and the element is dropped below 2; drafts add `items.<item_id>.state` and `state`
  - review_wall `{summary {average, count}|null, reviews: [{id, author, rating, title|null, body ≤600, created_at, product|null}]}` — approved reviews of products on sale only; `author` is first name + last initial
  - store_hours `{timezone}` (the organization's)
  - chart with a store source `{labels, series: [{id: "s1", name, values}]}`; only public counts (never sales, orders or customers)
  - An element without data is dropped publicly and gets `state: empty` in the draft.
- **`POST /builder/resolve`** also covers the five data elements and `chart`.
- **Contracts added:** `Reviews\ReviewShowcase` (approved reviews + star counts), `StorefrontCatalog::liveProductIds()`, `PromotionShowcase::claimed()`.
- **Templates:** 10 neutral sections (pricing, before/after, comparison, flash sale bar, bundle, team, review wall, photo grid, store hours + map, ratings). A template containing a flash sale bar `requires: promotions`; bundle items may use `product_ref`. 76 built-in templates.

**Render payload:** `{document: {id, key, title, version, source}, sections: <tree>, media: {<media_id>: {url, srcset, width, height, alt}}, data: {<element_id>: <homepage section object>}}`.
- Texts are resolved to the request language.
- Hidden and out-of-schedule nodes are removed, along with wrapped elements without content and any section left with no elements.
- `data` holds exactly what `/store/homepage` returns for a section of that type.
- Bootstrap includes `builder: {home: bool}`.
- The storefront serves landing pages at `/p/{slug}`.
