# Architecture

Enterprise POS is a **modular monolith**: one deployable Laravel application split into business modules with explicit boundaries, plus a React single-page application. There are no microservices.

```
┌──────────────────────────┐        HTTPS (same origin, /api/v1)        ┌────────────────────────────────────┐
│  React 19 SPA (Vite)     │ ─────────────────────────────────────────▶ │ Laravel 13 (PHP 8.4)               │
│  TanStack Query, Zustand │ ◀───────────── JSON envelope ───────────── │  app/Modules/*  (modular monolith) │
└──────────────────────────┘                                            └──────┬───────────┬────────────┬────┘
                                                                               │           │            │
                                                                        PostgreSQL 18    Redis      Queue workers /
                                                                        (system of       (cache,    scheduler
                                                                         record)          queues)
```

## 1. Guiding principles

1. **Correctness of money and stock first.** Every financial number is computed on the server with arbitrary-precision decimals, inside a database transaction, and persisted as `NUMERIC`.
2. **Business logic lives in the Domain and Application layers**, never in controllers, Form Requests, Eloquent models or React components.
3. **Modules talk through contracts and events**, not through each other's tables or models.
4. **Tenant isolation is enforced by the platform**, not remembered by each query.
5. **History is immutable.** Posted sales, ledgers and payments are never edited; corrections are new entries (returns, reversals, adjustments).
6. **The POS keeps working when optional parts fail** (AI provider, Redis-backed cache, notifications).

## 2. Backend layering (per module)

```
app/Modules/<Module>/
  Domain/            Entities, value objects, domain services, domain events, repository interfaces, rules.
                     Pure PHP. No Laravel facades, no HTTP, no Eloquent.
  Application/       Use cases (actions/services), DTOs, application-level contracts exposed to other modules.
                     Orchestrates domain + repositories inside transactions. Dispatches events.
  Infrastructure/    Eloquent models, repository implementations, migrations, external clients, listeners, jobs.
  Presentation/      HTTP controllers (thin), Form Requests, API Resources, Policies, routes (Routes/api.php).
  Tests/             Unit + Feature tests for this module.
  <Module>ServiceProvider.php   Binds contracts, registers events/policies. Extends ModuleServiceProvider.
```

Dependency direction: `Presentation → Application → Domain ← Infrastructure`. The Domain depends on nothing; Infrastructure implements Domain interfaces.

A request flows: **Route → Form Request (shape validation) → Controller → Application action (business validation, transaction) → Domain → Repository → API Resource → `ApiResponse` envelope**.

### Module registration

Each module has a `<Module>ServiceProvider` listed in `backend/bootstrap/providers.php`. Adding a module = create the folder, extend `ModuleServiceProvider`, register it there. See [MODULE_STRUCTURE.md](MODULE_STRUCTURE.md).

### Cross-module communication

| Need | Mechanism | Example |
|------|-----------|---------|
| Synchronous query/command | Interface in the provider module's `Application/Contracts`, bound in its service provider | Sales asks `Inventory\Application\Contracts\StockReservation` to deduct stock |
| React to something that happened | Domain event + listener in the consuming module | `SaleCompleted` → Loyalty awards points, Notifications alerts low stock |
| Reporting across modules | Read-only aggregate queries in the Reports module (read-model exception below; no views, Phase 7 §3t) | `Reports\Application\Support\SalesFacts` |

| Orchestrating a use case that spans modules | Call the other module's `Application/Actions` (its public API) inside one transaction | `ProvisionOrganization` → `Branches\CreateBranch` + `Users\ProvisionSystemRoles` + `Users\CreateUser` |

Foreign keys across module tables are allowed (referential integrity matters more than purity), but a module never writes another module's tables and never imports another module's Eloquent models. Read access goes through directory contracts (`BranchDirectory`, `OrganizationDirectory`, `ProductDirectory`, `SupplierDirectory`, `UserDirectory`, `BatchDirectory`). Documented exceptions:

- the Authentication module operates on the Users module's `User` model (it is Laravel's auth model);
- `ProvisionOrganization` receives the `User` returned by the Users module's `CreateUser` action, and `pos:permissions:sync` (Users) iterates `Organization` rows — both are provisioning/maintenance paths, not request paths;
- **read models may join foreign tables read-only** when a directory round-trip would make a list unfilterable — e.g. `GET /inventory/stock` joins `product_variants` to filter by search text and reorder level; SC1: `GET /purchasing/supplier-products` and `GET /inventory/reorder-rules` join `product_variants` / `products` to order by product, and `ReplenishmentData` reads `product_variants.reorder_level` as the fallback rule. The join is confined to the presenting controller and never writes. Phase 7: the **Reports** module is a read model over other modules' tables by design — each report is one query class that reads sales, orders, stock, purchasing, payments and expenses tables read-only, always filtered by organization and branch scope, and writes nothing (§3t);
- model factories and tests may reference foreign models to build data.

### Permissions are declared by modules

Each module's provider returns its permissions from `permissions()` (e.g. `'users.manage' => 'Create users, …'`). They are collected in the in-memory `PermissionRegistry`, mirrored into the `permissions` table by `php artisan pos:permissions:sync`, and every registered permission is a Gate ability (`can:users.manage`, `$user->can('sales.void')`). Built-in roles are defined as glob patterns over the catalog (`products.*`), so permissions added by later phases flow into them on the next sync.

## 3. Multi-tenancy and data isolation

- **Model:** shared database, shared schema. Tenant-owned tables carry `organization_id`; branch-scoped tables also carry `branch_id`.
- **Tenant context:** the `tenant` middleware (`Organizations\…\ResolveTenant`) resolves the organization from the authenticated user (platform admins choose one with `X-Organization-Id`) and the active branch from `X-Branch-Id`, which must be an active branch of that organization the user may access (assigned, or holding `branches.access_all`). It also rejects deactivated users and suspended organizations on every request, so revocation is immediate even for live tokens. The context lives in the request-scoped `TenantContext` and is cleared when the request ends.
- **Ordering matters:** `ResolveTenant` is placed before `SubstituteBindings` in the middleware priority list (`bootstrap/app.php`), so route-model binding already runs under the tenant scope — `/users/{id}` of another organization is a 404, never a loaded model.
- **Enforcement:** the `BelongsToOrganization` trait adds a global scope filtering by the context organization and stamps `organization_id` on insert (refusing a mismatching one). Branch-limited users only see their assigned branches. Cross-tenant access is covered by `Organizations/Tests/Feature/TenantIsolationTest` (critical workflow #12).
- **Outside a request** (console, seeders, provisioning) no organization is in context and queries are unscoped; code that must act for a tenant uses `TenantContext::runAs($organizationId, fn () => …)`.
- **Defense in depth (Phase 9):** evaluate PostgreSQL Row-Level Security policies keyed on `SET LOCAL app.organization_id`.

## 3a. Catalog and master data (Phase 3)

- **Variants are the sellable unit.** A product groups variants (simple product = one variant); prices, SKU, barcodes and (from Phase 4) stock belong to the variant.
- **Prices and amounts are decimal strings end to end:** `NUMERIC` columns, `decimal:N` casts, string JSON, and a frontend formatter that groups digits by string manipulation. The frontend never computes money.
- **Cost prices are need-to-know:** `purchase_price` is only serialised for `products.view_cost`; the product editor requires it together with `products.manage`.
- **In-use checks are delegated to the database:** catalog rows are referenced with `ON DELETE RESTRICT`; `ReferentialIntegrity::deleteOrFail()` turns the FK violation into `IN_USE`, so the Catalog module never needs to know who references it.
- **Human-readable numbers** come from `SequenceGenerator` (row-locked `document_sequences`), the same mechanism invoices will use.
- **Races** that slip past validation hit unique indexes and are reported as `409 CONFLICT`.

## 3b. Inventory and purchasing (Phase 4)

- **One write path for stock.** Every stock change — adjustment, transfer, goods receipt, purchase return, and later sales and refunds — goes through the `StockLedger` contract (`Inventory\Application\Contracts`). Callers pass `StockChange`s (store, variant, optional batch, signed quantity, unit cost) and a `StockReference` (document type/id/number); the ledger returns the resulting movements.
- **Two tables, two roles.** `stock_levels` is the current balance per store × variant × batch (a projection, locked and updated in place); `stock_movements` is the append-only ledger with `balance_after` on every row, so history can be audited and levels rebuilt. A PostgreSQL trigger rejects `UPDATE`/`DELETE` on the ledger; the Eloquent model refuses them too.
- **Locking protocol.** The ledger refuses to run outside a transaction. It sorts changes by `store|variant|batch` (so two documents touching the same rows always lock in the same order and cannot deadlock), inserts a missing level row with `INSERT … ON CONFLICT DO NOTHING`, then takes `SELECT … FOR UPDATE` and checks availability **after** the lock. Outbound quantities beyond stock raise `INSUFFICIENT_STOCK` unless the store's branch has `allow_negative_stock`.
- **Valuation is weighted average cost** per level row, kept at 4 decimals: inbound `(q·avg + in·cost) / (q + in)` (or the inbound cost when stock was ≤ 0); outbound leaves at the current average, which is also the cost recorded on transfers and the basis for future COGS. Since SC3 goods receipts post at the landed unit cost and landed cost vouchers add value to a level without moving quantity (`StockValuation`, §3s).
- **Untracked items are skipped**, not rejected: services and products with `track_stock = false` produce no movement.
- **Batches and expiry.** Batch-tracked products need a batch number (with optional expiry) on the way in and an existing batch on the way out; the same batch number with a different expiry is `BATCH_EXPIRY_MISMATCH`.
- **Transfers are two-step** (dispatch → in transit → receive or cancel). Dispatch leaves the source at its average cost and stores that cost on the lines, so the destination receives exactly what left.
- **Purchasing documents.** A purchase order commits nothing to stock. A goods receipt is the supplier invoice: one transaction posts stock in, the payable, and the received quantities back onto the order (`partially_received`/`received`). Returns are limited per receipt line to the quantity not yet returned and leave at the receipt's unit cost and batch. Supplier balances and statements are computed from documents (opening balance + receipts − returns − payments), not stored, so they can never drift.
- **Low stock** is detected inside the ledger when a level crosses its reorder level downward. `StockFellBelowReorderLevel` is dispatched **after commit** (a rolled-back sale never alerts) and handled by a queued listener that notifies users holding `inventory.view` for that branch through Laravel database notifications (`/notifications`).

## 3c. POS and sales (Phase 5)

- **The server prices every cart.** The client sends variant ids, quantities, requested discounts and payments — never prices or totals. `CartPricer` loads current selling prices and tax rates, applies the discount rules and runs the pure `SaleCalculator`; the POS preview (`POST /pos/price`) and checkout use the same code, so they always agree to the cent.
- **Calculation order** per line: subtotal = quantity × price (rounded once) → item discount → share of the invoice discount (allocated in proportion with largest-remainder rounding, so shares add up exactly) → tax: added on top (exclusive) or extracted as amount × rate / (100 + rate) (inclusive, the organization's `tax_mode`, snapshotted on the sale). Invoice totals are sums of rounded line values.
- **Discount rules** (critical rule #4): manual discounts need `sales.discount`; an item discount may not exceed the product's max. discount %; the customer's group discount is applied automatically as the invoice discount and needs no permission. Violations are `DISCOUNT_NOT_ALLOWED`.
- **Payments** (`PaymentSettlement`): any mix of cash, card and mobile banking. Only cash can be over-tendered (change is taken from the last cash payments); a shortfall stays due and needs a customer, `sales.credit` and room in the customer's credit limit, checked under a per-customer advisory lock.
- **Checkout transaction** (`CompleteSale`, critical rules #1–3, #9): number the invoice from the branch's locked sequence row → post stock through the ledger (batch-tracked goods first-expiry-first-out, expired batches never) → write the invoice with its cost snapshot, batch allocations, serial numbers and payments. Anything failing (stock, credit, serial already sold) rolls everything back, including the invoice number.
- **Idempotency** (critical rule #5): `POST /pos/checkout` requires `Idempotency-Key`. The `idempotent` middleware claims the key before the controller runs, stores a successful response and replays it for retries with the same payload; a different payload with the same key is `409 IDEMPOTENCY_KEY_REUSED`, a concurrent duplicate `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`. Failed attempts release the key. The SPA keeps the key with the pending cart, so a retry after a time-out or reload cannot sell twice.
- **Immutability** (critical rule #6): lines, stock allocations and payments are append-only (model guards + PostgreSQL triggers). Cancelling a sale changes only its status: stock goes back to the exact batches at the cost it left with, payments get negative reversal entries, serials are released, and the cancellation is audited.
- **Visibility:** `sales.view` sees the sales of accessible branches; a POS-only role sees the sales it rang up. Cost figures need `products.view_cost`.

## 3d. Payments, returns, cash registers, expenses, loyalty (Phase 6)

- **One payments ledger.** Every amount of money received or paid out — sale payments, cancellation reversals, refunds, customer payments, expenses, other income, voids, cash in/out — is appended to `payments` (Payments module) through the `PaymentLedger` contract, inside the transaction of the document that moved it. Rows are immutable (direction + positive amount, method, source document, customer, register session). Loyalty points are value, not money: they have their own ledger in Loyalty and never reach `payments`.
- **Cash registers.** A register (till) belongs to a branch; a cashier runs one session (shift) at a time on one register, and a register has one session at a time (partial unique indexes). The session opens with a counted float; the ledger gives the expected cash (float + cash in − cash out); closing stores the counted cash and the variance (critical workflow #11). **Every POS checkout needs the cashier's open session in the store's branch** (`CASH_SESSION_REQUIRED`), and so does any cash leaving or entering a drawer (refund, cancellation, collection, expense); a payout cannot take the drawer below zero (`INSUFFICIENT_CASH`). Non-cash entries are linked to the session when one is open, so the session report (X while open, Z once closed) shows every method.
- **Returns** live in Sales, next to the invoices they correct (as purchase returns live in Purchasing). A return references its invoice and lines; quantities are capped at what is neither returned nor requested (pending requests reserve them). Each line is valued at its share of what the line actually charged (discounts and tax included, proportional and rounded; the last return of a line takes the exact remainder — `ReturnShare`). Without `returns.approve` a return is a pending request; an approver completes or rejects it (their own returns complete at once). Completion, in one transaction: restocked lines go back to the exact batches they were sold from at their cost (written-off lines bring no stock back), serials are released, the total is **first credited against what the customer still owes on the invoice**, the rest is refunded with the given methods (must add up exactly — `REFUND_MISMATCH`; card, mobile and points refunds capped at what was paid that way; cash from the approver's drawer). A sale with returns can no longer be cancelled.
- **Receivables.** Customer balance = opening balance + dues of completed sales − returns credited − customer payments (`CustomerCredit`, computed, never stored). Customer payments cannot exceed the balance (no advances) and are locked per customer like credit sales; the statement lists invoices, till payments, cancellations, returns, refunds and payments with a running balance.
- **Expenses and other income** (Expenses module): categorized, numbered `EXP-`/`INC-`, immutable; voiding books the opposite payment.
- **Loyalty** plugs into Sales by dependency inversion: Sales declares the `LoyaltyProgram` contract (bound to a no-op by default); the Loyalty module implements it, so Loyalty depends on Sales and not the other way round. Points are earned on the sale total minus points redeemed (`points_per_spend` for every full `spend_amount`, rounded down), redeemed as the `loyalty_points` payment method in whole points, and reversed with cancellations (all) and returns (the returned share of what was earned, cumulatively; points refunded at the rate they were redeemed at). Balances may go negative when earned points were already spent.

## 3e. Online storefront (e-commerce track, E4)

The e-commerce track (plan and decisions in `docs/ecommerce/`) adds a public storefront to the same application.

- **Tenant from the host name.** `storefront_domains` maps host → organization. The `storefront` middleware (`ResolveStorefront` in the Storefront module) puts that organization into `TenantContext`, so the existing organization scope protects every public query; unknown hosts, closed stores and suspended organizations are 404. Staff of the organization holding `storefront.view` can preview a closed store in the browser they are signed in with. Local hosts map to `STOREFRONT_DEFAULT_HOST` (ADR-001).
- **Configuration modules.** `Storefront` owns settings, domains, the theme document (schema-normalized JSON: defaults for missing keys, unknown keys dropped) with policy-checked custom CSS, and menus (one per location, whole-tree replacement, links restricted to site paths or http(s) URLs). `Media` owns the image library: random names on the configured disk, sha-256 de-duplication, WebP renditions by a queued GD job, `srcset` in every reference, and in-use protection — foreign keys where they exist, plus tagged `MediaReferences` checkers for ids kept in JSON (the theme).
- **One public read model.** `GET /store/bootstrap` returns everything the storefront needs before drawing a page; the HTML shell (`StorefrontShellController`, a module `web.php` route) serves the built `storefront.html` with title, description, canonical, Open Graph and favicon written on the server and the same payload inlined, so crawlers get metadata in the first byte and the SPA needs no extra round trip (ADR-008). Paths without a storefront page answer 404 + `noindex`.
- **Two SPAs, one build.** The back office moved under `/admin` (React Router `basename`); the storefront is a second Vite entry (`storefront.html` → `src/storefront/`) that never loads admin code (ADR-007).
- **Content and homepage (E5).** The homepage is a list of typed sections (`Domain\SectionType`: defaults, normalization and media references per type, value validation in the request); banner sections attach banners as ordered items. `GET /store/homepage` returns only live sections and drops sections with no live banner, so the storefront never draws an empty block; staff get the full list with each section's state as a preview. Section types are added only with the data and pages they link to (products in E6, deals in E8, blog in E11). The `Cms` module owns pages, FAQ, contact messages and the double opt-in newsletter; Storefront depends on it through `PageDirectory` (menu links to pages, page metadata in the shell) and protects linked pages through the tagged `PageReferences` contract — the same pattern as `MediaReferences`.
- **Rich text.** Staff-written HTML goes through the shared `HtmlSanitizer` contract (HTMLPurifier, ADR-009 whitelist; images only from the media disk) on every save, and is rendered as stored. The admin editor (TipTap) only offers what survives sanitizing.

## 3f. Online catalog (e-commerce track, E6)

- **Web data next to the POS catalog, not in it.** The `OnlineCatalog` module owns 1:1 web tables beside the POS records — `product_listings`, `variant_listings`, `category_listings`, `brand_listings`, `related_products` — plus the `product_stats` projection. Products, Catalog and Inventory know nothing about the online store. In the admin the web listing is a separate form under the product editor (saved on its own, `online_catalog.*`), also reachable on its own page `/admin/products/{id}/online-store` for online store staff without `products.manage`. The attribute dictionary (`attributes`, `attribute_values`) belongs to Catalog; products keep their own `options`/`option_values`, and an option is linked to an attribute by a case-insensitive name match.
- **Listing read model.** `Infrastructure/ReadModels/CatalogReadModel` loads the candidate set — live listings (published, inside their window) of active, non-archived products of the organization, narrowed in SQL only by search, category scope, ids or slugs — together with active variants, compare-at prices, images, stock and popularity in a handful of chunked queries. Filtering, disjunctive faceting (`Domain\FacetCalculator`, `CatalogFilter`), sorting (`CatalogSort`, always ending with name and id so pages are stable) and paging then run in PHP on plain `CatalogItem` values, so results are identical on SQLite (tests) and PostgreSQL. Scale assumption: a few thousand published products per organization; E12 revisits this with `EXPLAIN` on real data (candidates: SQL-side price/brand filters, a materialized facet table). Like the Inventory stock list, read models read other modules' tables (products, variants, images, stock, sales) read-only and filter every query by organization; writes always go through the owning module.
- **Contract for the Storefront module.** Storefront never touches catalog tables: homepage catalog sections, menu links to categories/brands, link-picker data, hand-picked item summaries and the shell's page metadata all come through the OnlineCatalog contract `StorefrontCatalog` (implemented by `ReadModelStorefrontCatalog`). Category images/banners and brand logos are protected from deletion by a tagged `MediaReferences` checker, as in E4/E5.
- **Availability.** The storefront's `fulfilment_store_id` names the stock location for online availability. A variant is in stock when its product does not track stock (or is a service) or when its sellable on-hand quantity there (Inventory `StockLevels::onHand`, expired batches excluded) is above zero. Without a fulfilment store, tracked products are out of stock. Exact quantities never leave the server: the API exposes `in_stock` and `low_stock` (1–5 left).
- **Prices.** The storefront shows the variants' `selling_price` as stored (decimal strings, never floats) and filters/sorts by the same number. The bootstrap's `store.prices_include_tax` reflects the organization's tax mode; in exclusive mode the product page says "Excl. VAT" and tax is added at checkout (E8). A compare-at price only counts while it is above the selling price, so a later price increase ends a sale instead of showing a negative discount.
- **Popularity.** `product_stats` holds net units (completed POS sales minus completed returns, each return counted in the period of the sale it reverses) for the last 30 days and in total, rebuilt per organization by the `RefreshProductStats` job; `storefront:refresh-product-stats` runs it hourly from the scheduler. It drives the *popularity* sort and the *best sellers* source; there is no rating column or sort until reviews (E10).
- **Search.** `q` is a case-insensitive substring match on product name, active SKU and brand name (`lower(...) LIKE`). On PostgreSQL a `pg_trgm` GIN index on `lower(products.name)` serves it; there is no `similarity()` ranking (results must match SQLite), and suggestions rank names that start with the term first.
- **Storefront pages.** `/shop`, `/search`, `/category/{slug}`, `/brand/{slug}` share one listing page whose filter state lives in the URL; `/product/{slug}` keeps the selected variant in `?variant=`. Recently viewed products are stored as slugs only (localStorage) and fetched fresh with `GET /store/products?slugs=`, so a price change shows everywhere.

## 3g. Customer identity, storefront sessions and cart pricing (e-commerce track, E7)

- **Shoppers are not users.** The `CustomerAccounts` module owns `customer_accounts` (1:1 `customers`, e-mail unique per organization regardless of case) and the session guard `customer` (provider `customer_accounts`, ADR-002). Sanctum's guard stays `['web']`, so a shopper session never satisfies `auth:sanctum`, and staff sessions are never shoppers. The guard's provider (`StorefrontCustomerProvider`) only looks accounts up while a storefront has put its organization into `TenantContext`; the account model carries the organization scope, so a session cookie of store A is anonymous on store B's host. `ResolveStorefront` and `storefront.session` are placed before `AuthenticatesRequests` in the middleware priority list for that reason.
- **One browser, two identities.** Sign-in calls `Auth::guard('customer')->login()` and regenerates the session id (fixation). Sign-out calls `Auth::guard('customer')->logout()` and `regenerateToken()` — never `invalidate()` — so a staff member signed in to the back office in the same browser stays signed in (covered by `CustomerSessionTest`). `customer.active` re-checks the account status and the customer record (archived, inactive) on every signed-in request and signs the shopper out, so staff disabling an account (`PATCH /customer-accounts/{customerId}`) takes effect at once; `customer.active:optional` downgrades such a request to a guest (cart, `me`).
- **Default guard side effect.** `auth:customer` makes `customer` the request's default guard, so `Auth::id()` would return a shopper's account id. Author columns (`TracksAuthor`) and the audit trail therefore ask `Shared\Application\Support\StaffActor::id()`, which returns an id only for staff users (`TenantUser`).
- **Sessions on storefront hosts.** Storefront hosts are not in `SANCTUM_STATEFUL_DOMAINS` (they are configured per organization at runtime), so the API group gives them no session. The `storefront.session` middleware runs the same stack Sanctum uses — `EncryptCookies`, `AddQueuedCookiesToResponse`, `StartSession`, `ValidateCsrfToken` — on the bootstrap, account, cart and wishlist routes only, with httpOnly, SameSite=Lax session cookies; it does nothing when Sanctum already made the request stateful (attribute `sanctum`, e.g. the storefront served from a stateful dev host). Catalog, CMS and geography reads stay sessionless and cacheable. The storefront client (`src/storefront/http.ts`) echoes `XSRF-TOKEN` as `X-XSRF-TOKEN` and, after a 419, refreshes the cookie with `GET /store/account/me` and retries once.
- **Registration never links POS customers** (ADR-018). Every sign-up creates a new `customers` row through the Customers module (`OnlineCustomerProfiles`, `CUS-` sequence) and its account in one transaction. The phone is copied to the customer only when no other customer of the organization uses it, so the till's phone lookup stays unique and the form never reveals a known number. Customers depend on nothing in CustomerAccounts: the customer screens read the account through the Customers-owned `CustomerOnlineAccounts` contract (bound to a null implementation by default, implemented by CustomerAccounts — the `LoyaltyProgram` pattern).
- **Tokens.** E-mail verification and password reset use random tokens stored as sha-256 (verification on the account row, 24 hours; reset in the module's own `customer_password_reset_tokens`, one per e-mail and organization, 60 minutes, keyed by organization and e-mail — instead of a Laravel password broker). Links point at the host the request came from. Answers to forgot-password and sign-in never reveal whether an e-mail is registered (same message, equalised hashing time). A reset rotates the remember-me token but cannot end other sessions (`logoutOtherDevices` needs the old password). Unverified accounts can sign in and shop; checkout does not require verification either (E8a).
- **Addresses and geography.** Addresses belong to Customers (`customer_addresses`, `CustomerAddressBook`): every operation is scoped to the signed-in shopper's customer id and serialized by a lock on the customer row (limit of 10, exactly one default shipping address). Divisions and districts are **global** reference data in the `Geography` module (no `organization_id`; `GeoDirectory` contract); the upazila/thana level is a free-text `area` until a licensed dataset is chosen (E8 shipping zones work at district level). Phones are normalized to `01XXXXXXXXX` by the shared `Shared\Domain\BangladeshMobile`.
- **Cart pricing (ADR-005).** Carts store variant ids and quantities only. `Cart\Application\Services\CartPricer` is the one pricing path: it loads every line's live data through `StorefrontCatalog::variantsForCart()` (listing state, price, compare-at, unit, tax rate, on-hand at the fulfilment store via Inventory `StockLevels`) and totals the countable lines with the POS `SaleCalculator` in the organization's tax mode and currency. It runs on every read and after every write, so the storefront never computes money and a price change or stock movement shows on the next request. Reads never change quantities: unavailable and out-of-stock lines stay flagged and count zero; lines above the stock count with what is available. Writes run in a transaction with the cart row locked; adding checks purchasability and stock (`VARIANT_NOT_PURCHASABLE`, `OUT_OF_STOCK`, `INSUFFICIENT_STOCK`). Stock is **not reserved** by a cart — it leaves only at order placement (ADR-004, E8).
- **Guest carts and merge.** A guest cart is found by the sha-256 of a random token in the httpOnly `cart_token` cookie; it is created on the first add and deleted by `cart:prune` 30 days after its last change. CustomerAccounts declares `GuestCartMerger` (no-op by default); the Cart module implements it, so sign-in, registration and password reset merge the cookie's cart into the customer's cart (summed, capped at stock and 999, 50-line limit) inside one transaction with the customer's cart locked, then forget the cookie. The guest wishlist never reaches the server until sign-in: the browser keeps product ids and slugs (no names or prices) and posts them to `/store/wishlist/merge`.

## 3h. Shipping, checkout and web orders (e-commerce track, E8a)

- **Modules.** `Shipping` owns delivery zones (sets of districts, one zone per district per organization — `DISTRICT_IN_OTHER_ZONE` in `ManageShippingZones` under a lock, backed by a unique index) and their methods; checkout asks it through `ShippingRates::methodsForDistrict()`, and `Domain\ShippingFee` computes the delivery fee (flat, free from `free_over` compared with the goods total after tax) and the COD fee. `OnlinePayments` owns the per-organization method configuration (`payment_gateways`) behind `CheckoutPaymentMethods` (`all`, `enabled`, `usable`, `initiate`) and the `PaymentGateway` drivers — in E8a only `CashOnDeliveryGateway` and `BankTransferGateway`, which never redirect (`GatewayInitiation::awaitsPayment` is true for bank transfer). `Orders` owns checkout, the order document and its workflow. Orders depends on Cart (`ShoppingCart`, `CartPricer`), Customers (`CustomerAddressBook`), Geography, Shipping, OnlinePayments, Inventory (`StockLedger`), Payments (`PaymentLedger`), Products, Branches, Users and Storefront (`StorefrontConfig`); none of them depends on Orders.
- **One pricing path** (ADR-005). `Orders\Application\Services\CheckoutQuoter` is shared by the preview and the placement: `CartPricer::quote()` (E7: live listing data, availability, `SaleCalculator` in the organization's tax mode) gives the cart view and the counted lines with their `SaleCalculator` amounts; the quoter adds the delivery fee of the chosen method for the address's district and the COD fee, after tax and untaxed in E8a. The client never sends a price — only `expected_total`, the total it showed, which the server compares with its own (`409 TOTAL_CHANGED` with the fresh preview). The preview tolerates partial input and auto-picks a district's only method; placement insists on the shopper's choice.
- **Placement transaction** (`PlaceOrder`, brief check 13). Outside the transaction: guest checkout allowed? fulfilment store active? Inside one `DB::transaction`: (1) lock the shopper's active cart (`ShoppingCart::lockForCheckout`, `FOR UPDATE`) — no cart or no lines → `CART_EMPTY`; (2) reprice through the quoter — any flagged line → `CART_HAS_ISSUES`; (3) resolve the address snapshot (a saved address of this customer or the inline one, district in division); (4) the delivery method must be offered for that district (`SHIPPING_UNAVAILABLE`); (5) the payment method must be usable (`PAYMENT_METHOD_UNAVAILABLE`); (6) compare `expected_total`; (7) number `WEB-000001` from the locked `document_sequences` row (key `web_order`); (8) post every line through `StockLedger::post` as `online_order` at the fulfilment store with batch allocation (stock rows locked in the ledger's deterministic order; `INSUFFICIENT_STOCK` aborts everything); (9) write `orders`, `order_lines` (snapshots, cost from the allocations or the purchase price for untracked products), `order_line_stock` (the allocations: batch, quantity, unit cost, movement id), `order_addresses`, the first `order_status_history` row; (10) mark the cart converted (lines deleted, `converted_order_id` set). Any failure rolls all of it back. After commit: an optional save of the inline address to the address book (best effort) and the `OrderPlaced` event (confirmation e-mail queued, staff inbox notification) inside a `try` — the order stands even if notifying fails.
- **Stock leaves exactly once** (ADR-004, brief check 14). Stock is posted only by a successful placement; the endpoint's idempotency makes a retried request replay the first answer instead of posting again. `MovementType::OnlineOrder` overrides the branch's `allow_negative_stock` (`forbidsNegativeStock()`), so the web never oversells; two checkouts racing for the last unit serialize on the stock row lock (`CheckoutConcurrencyTest`, PostgreSQL only). **Restock** (`CancelOrder`): with the order row locked, the status is checked (`INVALID_STATUS_TRANSITION` for a cancelled order, `ORDER_PAID` for a paid one) and each `order_line_stock` allocation goes back to its batch at its unit cost as `online_order_cancel` (inbound), in the same transaction as the status change — a second cancel, or a cancel racing the expiry job, finds the order cancelled and posts nothing.
- **Idempotency scopes** (ADR-014). `idempotency_keys` are unique per `(scope, key)`. Staff routes (`idempotent`) use `user:{id}`; storefront routes use `idempotent:shopper`, which asks the Shared interface `ShopperIdempotencyScope` (implemented by Cart's `CartIdempotencyScope`, which owns the cart cookie): `customer:{account id}` for a signed-in shopper, `cart:{sha-256 of the cart cookie token}` for a guest, and `422 CART_EMPTY` for a guest without a cart (nothing to check out, no scope). The guest scope survives the cart's conversion, so a retry whose response was lost still finds the stored 201. The storefront's `PlacementAttempts` keeps one key per attempt and reuses it only after an open outcome (network error, 5xx, `IDEMPOTENCY_REQUEST_IN_PROGRESS`); any change of the body or a definite answer starts a new key. Admin web order steps send a key per dialog submission, reused on a safe retry.
- **Order lifecycle** (ADR-003). `OrderStatus` encodes the transitions (`pending_payment → confirmed | cancelled`, `confirmed → processing | cancelled`, `processing → shipped | cancelled`, `shipped → delivered`; `failed` is reserved for gateways, E8c). `OrderWorkflow` runs every staff step with the order row locked, appends history (actor = staff user; `NULL` = shopper at placement or the system at expiry) and audits it. COD orders start `confirmed`; bank-transfer orders start `pending_payment` with `expires_at` = placement + `hold_hours`. `allowed_actions` in the staff view is derived from status, payment status and method, so the admin shows only valid buttons; the server re-checks anyway.
- **Money in the ledger** (ADR-006). Confirming a bank transfer and recording a courier's COD remittance call `PaymentLedger::recordSystem()` — entries that do not pass through a register drawer (no session, `created_by` = the confirming staff user or null for the system) — with method `bank_transfer` / `cash_on_delivery`, source `PaymentSource::ONLINE_ORDER` and the order total; cash-method entries are refused there (`CASH_SESSION_REQUIRED`). `PaymentLedger::entriesOf()` gives the order page its payments. A paid order cannot be cancelled; since E10b a delivered one can be returned and refunded (§3l) — a paid order before delivery still has no cancel-with-refund path.
- **Expiry job.** `orders:expire-pending` (scheduler, every minute, `withoutOverlapping`) lists up to 500 due `pending_payment` orders across organizations, then for each runs inside the order's tenant: re-select it with `FOR UPDATE SKIP LOCKED` on PostgreSQL (plain `FOR UPDATE` on SQLite) and still `pending_payment` and due, then `CancelOrder::cancelLocked()` with reason `payment_expired` and no actor. An order a staff member is confirming at that moment is skipped (locked) and re-checked on the next run; parallel runs never cancel or restock twice.
- **Guests and customers.** Guest orders keep `customer_id` NULL and a contact snapshot — no POS customer record is created (keeps the till's customer list and phone lookup clean). Signed-in orders carry `customer_id` and `customer_account_id`. A guest's order page needs a random 32-byte token returned once in the 201 and in the e-mail link; only its sha-256 is stored, compared with `hash_equals`; a wrong token is a 404 like an unknown number. The storefront keeps the token in `sessionStorage` per order number and removes it from the address bar.
- **Courier and tracking** were free text on the order in E8a; since E10a couriers and shipments exist (§3k) and the order keeps the text fields as a copy.

## 3i. Promotions (e-commerce track, E8b)

- **Module boundaries.** `Promotions` owns `promotions`, `promotion_targets`, `coupons` and `promotion_redemptions`, the staff API and three contracts in `Application/Contracts`: `PromotionPricing::price(lines, couponCode, customerId, email, currency)` → `PromotionQuote` (per-line product discount and promotion, order discount, free shipping, coupon status, the redemptions a placement would write), `CatalogPromotions` (`bestFor` a product at a unit price, `countdownPromotions`, `isCountdownPromotion`) and `PromotionRedemptions` (`lock`, `record` inside the caller's transaction). It depends only on Catalog (`CatalogDirectory`, the category tree for "categories include sub-categories"), Products (`ProductDirectory::products`, target names), Customers (`CustomerDirectory`, redemption names) and Organizations (base currency) — and, like Orders, reuses Sales' `AppendOnly` model trait. Cart, Orders, OnlineCatalog and Storefront depend on Promotions; Promotions depends on none of them. Callers pass what the rules need per line (`key, product_id, brand_id, category_id, quantity, unit_price`; `StorefrontCatalog::variantsForCart` now returns `brand_id`/`category_id`). Channel: **web only** — the POS (`Pos`/`Sales`) never asks for promotions.
- **Pure engine.** `Domain\PromotionEngine::apply()` takes the lines, the automatic offers, the coupon's offer (or why it is blocked) and `now`; no database, no clock, Money only. The rule: (1) each line gets the single best product-scope promotion (largest discount on that line; ties → earliest end, then id; percent of the line amount, fixed per unit capped at the line amount; `min_subtotal` against the matching lines' subtotal; `max_discount` shared out with `Money::allocate`); (2) the single best order-scope percent/fixed promotion on the subtotal after product discounts (`min_subtotal` before discounts); (3) free delivery when any free-shipping promotion is eligible (automatic preferred); (4) a valid coupon nobody uses gets `better_offer`. No stacking flags, priorities or customer groups. `PromotionOffers` (Infrastructure) turns rows into `Offer` values, loads targets and category descendants, filters automatic promotions whose total or per-shopper limit is reached and resolves the coupon (`CouponReason`); its caches and those of `EloquentCatalogPromotions` live for one request and organization.
- **One pricing path** (ADR-005). `CartPricer` asks `PromotionPricing` for the counted lines and feeds the result into the POS `SaleCalculator`: each line's product discount as its `Discount::amount`, the order discount as the invoice discount, so tax is computed after discounts and the per-line allocation is the calculator's. Cart reads, every cart write, the checkout preview and placement all go through it; `CheckoutQuoter` only adds delivery (waived by a free-delivery promotion: `shipping_discount` = the waived fee, shipping redemption only when it is above zero) and the COD fee (never waived). Applying a coupon prices the cart with the candidate code inside the cart lock and stores it only when the code is usable (or merely beaten — `better_offer`); a stored coupon that becomes invalid is reported and ignored, never blocking checkout.
- **Redemptions and locking.** `PlaceOrder` prices the locked cart, then `PromotionRedemptions::lock()` takes `FOR UPDATE` on the rows of the promotions it would use **that carry a usage limit** (sorted by id) and on the coupon row, and prices again under those locks — at most three rounds, in case the second pricing picks another limited promotion. Limits are thus counted while no other placement can redeem the same promotion; a limit reached meanwhile simply drops the promotion, the total changes and the existing `409 TOTAL_CHANGED` path answers. Unlimited promotions are never locked, so ordinary sales do not serialize on a popular promotion. The order then writes `order_promotions` (snapshot shown on order pages and in the e-mail) and `record()` appends one `promotion_redemptions` row per promotion and increments `coupons.used_count`, all in the placement transaction; the idempotent replay returns the stored answer without redeeming again. Per-customer limits count by `customer_id` for signed-in shoppers and by lower-case contact e-mail for guests (known only at checkout). Cancellation, expiry and online returns (E10b) leave redemptions in place.
- **Catalog display.** `CatalogReadModel` asks `CatalogPromotions::bestFor()` for each card and product variant: the engine run on one unit with the live automatic product-scope promotions whose total limit is not reached → `promotion {id, name, type, value, ends_at, show_countdown, price}` and `promo_price`. Coupon promotions and order-scope offers never show; per-customer limits are unknown there; a product promotion whose `min_subtotal` exceeds one unit's price does not show on cards, though the cart may still apply it. Listing filters, facets and sorts keep the base selling price (E12 may index promotional prices). The `hot_deals` homepage section (Storefront → `StorefrontCatalog::hotDealCards()`) lists live products whose card shows a live countdown promotion and counts down to the earliest end; the storefront hides it at zero and refetches the homepage.
- **Admin times.** Schedules are stored as instants (`Instants::normalize`); the admin edits them as `datetime-local` in the organization's timezone (`features/promotions/zoned-time.ts`).

## 3j. Customer account and reviews (e-commerce track, E9)

- **Own orders.** `Orders\Application\Queries\CustomerOrderHistory` reads orders by `orders.customer_id` (the customer record behind the signed-in account, set at placement while signed in) inside the host's organization (tenant scope); `find()` is the single entry point for the detail, cancel and re-order endpoints, so another customer's or another store's order is a 404 like an unknown number. Guest orders placed with the same e-mail are **not** attached — the e-mail address was never proven to belong to the account.
- **Cancel path reuse.** `CancelOwnOrder` opens a transaction, re-selects the order `FOR UPDATE` (still the customer's), checks the customer rule (`pending_payment` or `confirmed`, and `unpaid` — else `ORDER_NOT_CANCELLABLE`) and hands the locked row to the E8a `CancelOrder::cancelLocked()` — the same restock to the exact `order_line_stock` allocations, status change and audit as staff cancellation and expiry, now with `actor_type` `customer` (`staff` with an actor, `system` without). The endpoint sits behind `idempotent:shopper` (scope `customer:{account id}`), so a retried cancel replays the first answer and never restocks twice; a second, different request finds the order cancelled. After commit the `OrderCancelledByCustomer` event's listener sends the queued cancellation e-mail and the staff inbox notification (`web_orders.view`).
- **Re-order** goes through the cart's own write path: `ShoppingCart::addLines()` (Cart) locks the customer's cart, merges quantities under the usual rules (`CartRules::merged`, stock cap, 999, 50 lines) and reports skipped lines instead of failing; `CartPricer` then prices the cart as always, so re-ordered lines carry today's prices and promotions.
- **Reviews module and dependency direction.** `Reviews` owns `reviews`, the customer/public/staff endpoints and the `reviews` rate limiter. It asks Orders through `Orders\Application\Contracts\PurchaseVerifier::deliveredLine(customerId, productId)` (implemented by Orders' `EloquentPurchaseVerifier`: the customer's most recent delivered web order line of the product) and OnlineCatalog through `StorefrontCatalog` (`liveProductId(slug)`, `productSummaries(ids)`), Customers through `CustomerDirectory::summaries` (name, e-mail) and Users through `UserDirectory::names`. Orders and OnlineCatalog must not depend on Reviews, so the data they show flows the other way through contracts **they** declare and Reviews implements: Orders' `OrderLineReviews::ofCustomer()` (the customer's review per product on the account order page; default `NoOrderLineReviews`) and OnlineCatalog's `ProductRatings::summary()` (the product page's `rating`; default `NoProductRatings`). The defaults are bound with `bindIf` and replaced by `ReviewsServiceProvider` (registered after Orders), so either module works without Reviews. The staff search reads the `products` and `customers` tables read-only (organization-scoped sub-selects) to filter by name and e-mail — the read-model exception of §2.
- **Moderation.** `ModerateReview` locks the review row; approve and reject are no-ops when the review already has that status (idempotent by state, no key needed) and are audited. An author's edit sets the review back to `pending` and clears the moderation columns (the PostgreSQL CHECK ties `moderated_at` to non-pending status). Only approved reviews are public; the summary is an aggregate over them per request (not cached in E9 — sized for the catalogue target; since E10b cards and the rating sort use a batched grouped query, §3l; E12 may add a projection).
- **Privacy of author names.** The public list never exposes the customer id, e-mail or full name: `Domain\ReviewAuthor::publicName()` reduces the customer's name to the first name and the last name's initial ("Rina Akter" → "Rina A.", empty → "Customer"). Staff see name and e-mail. Review text is stored as trimmed plain text, not HTML; the clients render it as text (React escaping), so nothing is sanitized server-side.

## 3k. Fulfilment (e-commerce track, E10a)

- **Ownership.** Couriers are reference data of the **Shipping** module (`couriers`, `ManageCouriers`, `Domain\TrackingUrl`); shipments, their events and COD remittances belong to **Orders**, because they are steps of the order lifecycle and change order state in the same transaction. Orders reads couriers only through `Shipping\Application\Contracts\CourierDirectory` (`find`, `summaries`, `trackingUrl`), bound by `ShippingServiceProvider`; Shipping knows nothing of Orders — the `RESTRICT` foreign keys from `shipments` / `cod_remittances` to `couriers` turn a delete of a used courier into `IN_USE` through the shared `ReferentialIntegrity` helper.
- **Shipments.** `OrderWorkflow::ship()` validates an active courier, then — with the order row locked — moves `processing → shipped` (the order keeps `courier_name` and `tracking_number` for lists, e-mails and the storefront), creates the `shipments` row (`cod_amount` = total of an unpaid COD order, else 0) and the first `shipment_events` row `handed_over`. `shipmentEvent()` locks the order, then the shipment, and follows `Domain\ShipmentStatus` (`handed_over`/`in_transit` → `in_transit`/`delivered`/`returned`; the last two are final). `delivered` goes through the same `deliverLocked()` as `/deliver`, so the order and the parcel agree. `returned` leaves the order `shipped`; `CancelOrder::returnedToSender()` then admits it to the E8a cancel path (still unpaid only), which restocks the exact `order_line_stock` allocations once. Orders shipped before E10a have no shipment: tracking updates answer `SHIPMENT_NOT_FOUND`, `/deliver` still works.
- **Board and bulk.** `GET /web-orders` builds one filtered query (payment method, courier via the shipment, district via the shipping address, placed-at days in the organization's timezone, search) and runs it twice more for `meta.status_counts` (grouped by status without the `status` filter, and the `cod_unremitted` count). `ProcessOrdersInBulk` calls `OrderWorkflow::process()` per order — each with its own transaction, lock, history and audit — and reports a result per order, so one order in the wrong state never blocks the rest.
- **Shared COD payment path.** `OrderWorkflow::recordCodPaymentLocked()` is the only code that marks a COD order paid: ledger `PaymentLedger::recordSystem()` with method `cash_on_delivery`, source `online_order`, the order total, then `payment_status = paid` and the audit entry. The manual *Record COD payment* (own riders) wraps it in its own lock; `RecordCodRemittance` calls it for each order it has already locked. The remittance transaction: lock the orders in id order, check all of them (`REMITTANCE_INVALID` with a reason per order, nothing written), sum the gross with `Money`, check the fee against it, take the `REM-` number, book the fee, write the remittance and its lines, pay each order, audit `cod_remittance.recorded`. The endpoint is idempotent (`idempotent` middleware); `cod_remittance_lines (organization_id, order_id)` is unique as a backstop.
- **Expenses contract and dependency direction.** The courier fee is an expense, so Orders asks the Expenses module through `Expenses\Application\Contracts\ExpenseRecorder::recordSystemExpense()` (implemented by `RecordSystemExpense`, bound in `ExpensesServiceProvider`): it joins the caller's transaction, finds or creates the category "Courier fees" (case-insensitive), numbers the expense `EXP-…`, records the outgoing ledger entry through `recordSystem()` (no register drawer; method `cash_on_delivery` — the fee was withheld from the collected cash) and audits it. Orders → Expenses and Orders → Shipping; neither Expenses nor Shipping depends on Orders. The remittance keeps `expense_id` and `expense_number`.
- **Printing without a PDF library.** `GET /web-orders/print` returns data only (`OrderPresenter::printable()`: a packing slip has no price keys at all; an invoice adds line amounts and totals; the organization header comes from `OrganizationDirectory::summary()` — legal name, address, phone, e-mail, tax/BIN number — and the storefront theme logo through `MediaLibrary`). The admin route `/web-orders/print` renders print-ready HTML outside the admin layout with `@media print` CSS (A4, a page break per order) and opens the browser's print dialog; "Save as PDF" is the browser's. Nothing is recorded when printing. A server-side PDF engine can come later without changing the endpoint.
- **Tracking links.** `TrackingUrl::build()` substitutes the `rawurlencode`d tracking number into the courier's template; templates are validated as absolute http(s) URLs (and by a PostgreSQL CHECK), so the storefront's *Track parcel* link (`tracking_url` on the guest and account order views) cannot become a `javascript:` URL. The link opens in a new tab with `rel="noopener"`.
- **Permissions.** `web_orders.remit` (new) guards `/cod-remittances*` and the admin page; the built-in Accountant role holds it with `web_orders.view`, Online Store Manager through `web_orders.*`. Reading couriers needs `shipping.manage` or `web_orders.view` (the ship dialog), changing them `shipping.manage`.

## 3l. Online returns and refunds (e-commerce track, E10b)

- **Ownership and flow.** Returns belong to **Orders** (`OrderReturnWorkflow`, `ReturnPolicy`, `ReturnPresenter`; tables `order_returns`, `order_return_lines`, `order_return_line_stock`, `order_return_history`). `Domain\ReturnStatus` encodes `requested → approved | rejected | cancelled`, `approved → received`, `received → refunded` (`INVALID_STATUS_TRANSITION` otherwise). A customer (`POST /store/account/orders/{number}/returns`) or staff (`POST /web-orders/{id}/returns`) request; staff approve (lower quantities, optional shipping refund) or reject; the customer may cancel while `requested`; staff receive (restock or write-off per line) and refund. The order status stays `delivered`; only its payment status and `refunded_total` change. Each step is one transaction that locks the **order row, then the return row** (one lock order everywhere), appends `order_return_history`, audits (`web_order_return.*`) and sits behind `idempotent` / `idempotent:shopper`.
- **Eligibility** (`ReturnPolicy`). `delivered`, money received (`PaymentStatus::isPaid()` — `paid` or a partial refund; `unpaid` → `not_paid`) and within `return_window_days` of `delivered_at` (Storefront's `StorefrontConfig`; `0` → `returns_disabled`). Staff may override the window and a disabled window with `override_window` and a mandatory note (audited, stored on the return); delivery and payment are never overridden. What a line can still return = ordered − quantities of the order's active returns (not rejected or cancelled), computed under the order lock (`QUANTITY_EXCEEDS_RETURNABLE`).
- **Proportional amounts.** Each return line is valued with the POS rule (`Sales\Domain\ReturnShare`, Phase 6): the share of what the order line charged — `line_total` (after its product and order discount, tax included), `tax_amount` and `cost_total` — for the returned quantity, with the exact remainder going to the return that takes the last unit, so the sum of all returns of a line equals the line. Approval re-values lines against the other active returns. Delivery and COD fees are outside the lines; staff may add `shipping_refund` at approval, capped by `shipping_total` minus the shipping refunds of the order's other active returns. `refund_amount = items_amount + shipping_refund` (PostgreSQL CHECK). Promotion redemptions and coupon usage are not reversed.
- **Exact restock.** At receipt each restocked line walks the order line's `order_line_stock` allocations (the batches and unit costs the sale took, E8a) and, per allocation, takes at most what earlier returns have not already put back (summed from the append-only `order_return_line_stock`). One `StockLedger::post()` call posts all of them as `MovementType::OnlineReturn` (inbound, at the allocation's unit cost, reference `online_return` / return number) at the order's store, and each piece is recorded in `order_return_line_stock` with its movement id. Lines marked `restock: false` are written off — no stock movement. More than the allocations hold is a programming error (`LogicException`), never a silent over-restock.
- **Refunds through the payments ledger** (ADR-006). `refund()` checks `refunded_total + refund_amount ≤ paid_total` (`REFUND_EXCEEDS_PAID`) under the order lock and writes one ledger entry out, source `PaymentSource::ONLINE_ORDER_REFUND`, reference id = the return, method mapped by `Domain\RefundMethod::ledgerMethod()`. Bank transfer and mobile banking use `PaymentLedger::recordSystem()` (no drawer, like COD remittances). **Cash** uses `PaymentLedger::record()` with the refunding user: it needs that user's open register session in the order's branch (`CASH_SESSION_REQUIRED`) and enough cash in it (`INSUFFICIENT_CASH`), so cash refunds show up in the shift's cash count. Then `refunded_total` grows and payment status becomes `partially_refunded` or, when refunds equal `paid_total`, `refunded`. `isPaid()` replaced the `=== Paid` checks in cancel, COD payment and remittance code so a refunded order is never treated as unpaid. The staff order and return pages list refunds from `PaymentLedger::entriesOf()`.
- **Paid cancellations (E11).** `CancelOrder::cancelWithRefund()` cancels a paid order (`PaymentStatus::isPaid()`) that is not delivered — `confirmed`/`processing`, or `shipped` with a returned parcel (`cancellableWithRefund()`). One transaction, order row locked: the amount is `paid_total − refunded_total` (`Money`), paid out by `Application\Services\RefundPayout` — the single refund path, shared with `OrderReturnWorkflow::refund()` (same ledger source `online_order_refund`, same cash rule: the user's open register session in the order's branch) — then the exact restock and closing shared with unpaid cancellations (`restockAndClose()`: `online_order_cancel` to the `order_line_stock` batches, `cancelled`, status history), `payment_status = refunded`, `refunded_total = paid_total`, audits `web_order.cancelled` and `web_order.refunded`. No `order_returns` row is written: nothing was delivered, so there is nothing to return. After commit `OrderCancelledWithRefund` → `SendOrderCancelledWithRefundNotifications` → queued `OrderCancelledWithRefundEmail` (the listener passes everything the template reads, including `cancel_reason`, which the storefront order view does not carry). Authorization is per order in the controller: unpaid → `web_orders.manage`; paid → `web_orders.refund` (alone suffices) and a `refund` body (`REFUND_REQUIRED` with the amount). Customer self-cancel (`ORDER_NOT_CANCELLABLE`) and the expiry job stay unpaid-only; `cancelLocked()` still refuses paid orders (`ORDER_PAID`). Promotion redemptions are not reversed.
- **Notifications.** After commit, `OrderReturnRequested` (customer requests only) → database notification to users with `web_orders.refund` (link `/web-returns/{id}`); `OrderReturnUpdated` (approved, rejected, refunded) → queued `OrderReturnStatusEmail` to the order's contact e-mail, linking to the account order page on `StorefrontConfig::primaryUrl()` when the order has a customer.

- **Permissions and UI.** `web_orders.refund` (new) guards every return write; `web_orders.view` reads returns. Accountant holds it explicitly, Online Store Manager through `web_orders.*`. Admin: *Web returns* (`/web-returns`, named apart from the POS *Returns*), a returns card and *Create return* on the web order page, *Web activity* on the customer sheet, *Report* tab on the promotion editor (HTML table, no chart library). Storefront: *Return items* dialog and returns card on the account order page, `/account/returns`, stars on cards and *Top rated*.

## 3n. SEO and caching (e-commerce track, E12a)

- **Shell and JSON-LD.** `StorefrontShellController` still renders every storefront page (ADR-008) and now adds schema.org JSON-LD built by `Presentation\Http\Support\StructuredData`: `Organization` on every page, `WebSite` + `SearchAction` on `/`, `Product` + `BreadcrumbList` on products, `CollectionPage` + `BreadcrumbList` on categories and brands, `BlogPosting` + `BreadcrumbList` on posts, `BreadcrumbList` on content pages and blog categories. Noindex pages get `Organization` only. Documents are encoded with `JSON_HEX_TAG|JSON_HEX_AMP` so store text cannot end the `<script>` element. Product data (offers per variant with the automatic-promotion price and `priceValidUntil`, availability from the storefront stock flags, rating from approved reviews, category breadcrumbs) comes from OnlineCatalog through `StorefrontCatalog::pageMeta()` (`ProductPage`); descriptions are plain text from `Shared\Domain\PlainText` (meta ≤ 160, Product ≤ 5000).
- **Index rules.** Canonical = the URL without its query; listings keep `?page=N` (N > 1). A listing with filters or a sort (tracking parameters `utm_*`, `gclid`, `fbclid`, `msclkid`, `ref` ignored), search, private and utility pages, 404s, previews and — with `storefront_settings.allow_indexing` false — every page get `<meta name="robots" content="noindex, follow">` and `X-Robots-Tag: noindex`.
- **Crawler files.** `StorefrontSeoController` (Storefront `web.php`, no session middleware): `robots.txt` answers any host — an indexable store (open, `allow_indexing`, primary domain) lists the disallowed personal and utility paths and the sitemap, anything else `Disallow: /`. `StorefrontSitemap` builds the sitemap index and `pages`, `products-N` (5000 per file), `categories`, `brands`, `blog` from OnlineCatalog (`sitemapEntries()`), Cms (`PageDirectory` / `BlogDirectory::sitemapEntries()`) — only live records, absolute URLs on the primary domain, product images in the image-sitemap namespace. Non-indexable → 404. `public/robots.txt` is gone; the web server must hand `/robots.txt` and `/sitemap*.xml` to PHP.
- **Content version (server cache).** Shared contract `StorefrontContentVersion`, implemented by Storefront's `Infrastructure\Caching\CacheStorefrontContentVersion` on the default cache store (ADR-012 as built): a per-organization counter `storefront:{org}:version` (seeded with the current time in milliseconds when missing, so an evicted counter never reuses an old value) and entries under `storefront:{org}:v{version}:{key}` — `bootstrap`, `homepage` (public only), `catalog:products:{hash of category ids}` (the live candidate set of shop, category and brand listings, related products and catalog homepage sections; facets are computed from it, text search and id / slug lookups are not cached) and `sitemap:{name}:{base}`. A bump makes every entry of the organization unreachable at once; no cache tags, so it works on the database, file, array and Redis stores. Lifetime: until the next bump, `TTL` 600 s, or `ContentSchedule::nextChange()` — the next instant a banner, homepage section, the announcement, a listing window, an automatic promotion, a blog post or a page goes live or ends — whichever comes first (scheduled content appears on time without a write).
- **What bumps.** `bump()` runs after commit (never on rollback). The `Shared\…\Concerns\ChangesStorefrontContent` model trait bumps on every create, effective update or delete of: products, variants, product images, categories, brands, attributes and attribute values, product / variant / category / brand listings, related products, promotions, promotion targets and redemptions, reviews (only when entering or leaving `approved`), banners, homepage sections and items, menus and menu items, theme, storefront settings and domains, CMS pages, FAQ items, blog categories and posts, media, the organization. Query-builder bulk writes fire no model events, so their actions bump explicitly (attribute values, related products, promotion targets, banner / section reorder, section items, menu items, the rating projection). Stock movements call `stockChanged()`, which bumps only for the storefront's fulfilment store.
- **Cache rule: no Eloquent objects.** `cache.serializable_classes` is `false`, so a serializing store returns incomplete objects for any class. Cached values are arrays and scalars only; the candidate set stores each listing's raw attributes and rehydrates with `newFromBuilder()`. `StorefrontSeoTest::test_cached_reads_survive_a_serializing_cache_store` runs the cached reads twice on a file store — the array store used by tests keeps objects and would hide the bug.
- **HTTP caching.** `StorefrontHttpCache` (alias `storefront.cache`, opted in per route group in OnlineCatalog, Reviews, Cms and Storefront) adds a weak `ETag` (xxh128 of the body without `request_id`) and answers `304`; `Cache-Control` is `public, max-age=60, stale-while-revalidate=300` for anonymous answers, `private, no-cache` when a session or cookie is involved (the bootstrap), `no-store, private` without ETag for previews or when the controller set `no-store`. The ETag is computed after the controller ran, so a 304 saves bandwidth, not server work (the server cache does that). Crawler files set their own headers (`robots.txt` 1 h, sitemaps 10 min).
- **Client head manager.** `src/storefront/use-document-meta.ts` — `useDocumentMeta({title, description, image, canonical, noindex, type})` and `privatePage(title)` — applies the same title, description, canonical, robots and `og:*` rules on in-app navigation (`null` while loading; store defaults restored on unmount; noindex everywhere in preview or when `store.allow_indexing` is false). JSON-LD stays server-only (first load).
- **Loading performance.** `MediaImage` lazy-loads with `decoding="async"`, `sizes` and intrinsic `width`/`height`; `priority` (eager, `fetchpriority="high"`) only on the LCP image (first hero slide, product main image, blog post cover, category banner). `lazyPage()` in `src/storefront/routes.tsx` splits content, blog, newsletter, cart, wishlist, checkout, order and account pages (`React.lazy` + Suspense with an accessible loading view); the product lightbox loads on first open. Home, listings and product pages stay in the entry chunk. No third-party preconnects (none used). Lighthouse is not measured (needs a new dependency).

## 3o. Localization (e-commerce track, E12b)

- **Languages.** `en` is the base language (base columns hold English, always enabled); `bn` is enabled per store (`storefront_settings.bangla_enabled`, default on) with `default_locale` (`en|bn`, must be enabled) and `bangla_digits` (display only). Content translations are optional `translations` jsonb documents `{"bn": {field: value}}` on the records shoppers read (listings, pages, FAQ, blog, menu items, banners, homepage sections, delivery and payment methods, promotions; the announcement inside the theme document).
- **`LocaleContext`** (`Shared\Application\Localization`, bound `scoped` — one per request / job). Default state: English only, current `en` — so staff requests, console commands and queued jobs read base values without doing anything. Only Storefront's `ResolveStorefront` middleware configures it (`configure(banglaEnabled, default, locale, digits)`) and resets it afterwards; every storefront answer gets `Content-Language`. Helpers: `resolve()` (static: a requested value or the default), `current()`, `defaultLocale()`, `enabled()`, `banglaEnabled()`, `banglaDigits()`, `runAs($locale, fn)`, `ogLocale()` (`bn_BD` / `en_US`).
- **Resolution rules.** JSON API requests (`/api/v1/store/*`) take the language from `?lang=` **only** — the language is part of the URL, so browser and CDN caches and the ETag stay correct without `Vary`. HTML requests (shell, sitemaps) take `?lang=` > `lang` cookie > `default_locale`; the shell answers with `Vary: Cookie`. Unknown, missing or disabled values fall back to the default (`en` while Bangla is off). The SPA writes the cookie, so it is excluded from `EncryptCookies` (`bootstrap/app.php`).
- **One fallback rule** (`Shared\Domain\Translations`): `pick($record, $field, $locale)` / `pickMany()` / `value($translations, $field, $locale, $base)` return the translation when it is a non-blank string, else the base value — per field, never per record. It accepts models (only selected columns: a row loaded without `translations` reads base values), row arrays and row objects, and decodes JSON strings from raw queries. Read models call it with `LocaleContext::current()`; no ad-hoc lookups. Slugs are never translated (one URL per record, language by `lang`). Staff input goes through `Shared\Application\Support\TranslationInput` (`rules()` with the base field's limits per entity constant `TRANSLATABLE`, `apply()` partial merge / blank removal / HtmlSanitizer for rich text, `present()` for staff payloads). `FixedText` holds the handful of words the server itself writes into titles and breadcrumbs.
- **Placement in the base language.** `PlaceOrder` records the request's language in `orders.locale`, then runs the placement inside `LocaleContext::runAs('en')`, so product, delivery-method, promotion and place-name snapshots are English whatever the shopper reads. Sign-up / sign-in store `customer_accounts.preferred_locale`. Both exist for localized e-mails (E13); e-mails are English today.
- **Cache per language.** `CacheStorefrontContentVersion` keys are `storefront:{org}:v{version}:{locale}:{key}` (the locale comes from `LocaleContext`), and `StorefrontHttpCache` hashes `{locale}|{body}` into the weak ETag, so an English and a Bangla answer never share a cache entry or an ETag. One content version still invalidates both languages.
- **Shell / SEO.** `<html lang>`, localized meta and `og:*`, `og:locale` + `og:locale:alternate`, hreflang `en` / `bn` / `x-default` on indexable pages while Bangla is on (the non-default language adds `?lang=`; x-default = the default language's URL), canonical in the page's language, JSON-LD `inLanguage`; sitemaps add `xhtml:link` alternates per URL. The shell's inline bootstrap is in the page's language.
- **Client dictionary.** `src/storefront/i18n/en/*.ts` (one namespace per area, keys `namespace.key`) merged into `en`; `bn/*.ts` typed as `Translations<typeof enNamespace>` — a missing or extra key is a type error, plural messages must stay plural (`{one, other}` via `Intl.PluralRules`). `t(key, vars)` interpolates `{name}` and formats numeric vars for the locale. English ships in the entry chunk; `bn.ts` is a lazy chunk loaded on first use (`dictionaries.ts`; the previous dictionary stays on screen while it loads, English on failure). `useLocale()` exposes `locale`, `locales`, `setLocale`, `t` and formatters.
- **Locale controller and requests.** `useLocaleController()` (storefront layout) resolves `?lang=` > cookie > store default within `store.locales`, loads the bootstrap in that language and publishes the locale to `i18n/runtime.ts` during render, before children query. `http.ts` adds `lang` to every `/store/*` request (an explicit `lang` wins). Every storefront query key ends with the locale (`localized()` in `store-keys.ts`), so switching refetches what is on screen and never shows one language's data under the other; `setLocalizedData()` drops other-language copies after a write. Switching writes the cookie (1 year, `SameSite=Lax`), replaces `?lang=` in the URL (dropped for the default) and sets `<html lang>`.
- **Digits and formatting.** The server never formats numbers (amounts stay NUMERIC strings). `i18n/format.ts` formats with `Intl` (`en-BD`, `bn-BD`) and `numberingSystem: 'latn'` unless the store turned Bengali digits on for Bangla (`beng`); `৳` first in both languages; lakh grouping in Bangla.
- **Fonts.** `storefront.css` imports the Bengali subset of Hind Siliguri (400–700) and Baloo Da 2 (variable) from Fontsource and applies them under `:lang(bn)` (body / headings) in front of the theme fonts; they are fetched only on Bangla pages, per `unicode-range` (Hind Siliguri ships only its Bengali subset, so Latin body text keeps the theme font; Baloo Da 2 ships all subsets, so Latin text inside Bangla headings is set in it too). English pages are unchanged.
- **Admin.** The back office stays English. `src/features/translations` provides the shared "বাংলা (Bangla)" editor section (`BanglaTranslations`, `BanglaInput`, helpers in `translations.ts` that build `translations: {bn: …}` and map `translations.bn.*` errors) used by every translatable editor; *Online store → Settings → Languages* edits the three settings.

## 3p. List exports (X1)

- **One query, two outputs.** A list controller applies its filters and `ListQuery::apply()` (search + sort); the JSON answer pages that query (`->paginate(ListQuery::perPage())`), and `?export=xlsx|pdf` (`ListExporter::requested()`, validated) hands the same query to `ListExporter::download($request, $format, <Module>Export::class, RowSource::fromQuery($query, $present))`. Scoping, permission and filters are therefore exactly the list's. Lists computed in memory (customer and supplier statements, valuation, promotion report) use `RowSource::fromRows()`.
- **Streaming rows.** `RowSource::fromQuery()` counts first (limits apply before any row is read), adds a primary-key tie-breaker to the sort when it is not already there (not on grouped queries), then reads `forPage()` chunks of `exports.chunk_size` (500) and passes each chunk through the list's own presenter — the exported values are what the JSON list returns, including names looked up per chunk. Rows are yielded one by one as arrays.
- **Definitions.** `<Module>\Presentation\Http\Exports\*Export extends ListExport`: `name()` (filename stem and audit list name), `title()`, `columns()` (`ExportColumn::text|number|money|quantity|date|dateTime|status|yesNo`, a dot path into the presented row or a closure) and `filters()` (`FilterSummary`: search, plain values humanized, ids shown by name through directories, booleans, flags, date ranges). Module base classes (`SalesListExport`, `PurchasingListExport`, `InventoryListExport`, `PaymentsListExport`) share filter vocabulary. Cost columns are added only when `Gate::allows('products.view_cost')`.
- **Exporter.** `ListExporter` throttles (`exports|{user id}`, `exports.rate_limit` per minute, applied inside because the same routes serve the JSON list), checks `exports.max_rows.{format}` (`EXPORT_TOO_LARGE`), builds an `ExportDocument` (title, columns, row stream, total, filter lines, letterhead, organization timezone, generated-at, user name), runs the writer, records `export.created` through `AuditTrail` and sets `Content-Type`, `Content-Disposition` (`<stem>-<org slug>-<YYYYMMDD-HHmm>.<ext>`), `Cache-Control: no-store, private` and `X-Export-Rows`. Controllers return a Symfony `Response` (JSON through `ApiResponse` or the file).
- **Values.** `ExportValues` turns presented values into exact decimal strings (money stays a string until the Excel cell — the only place it becomes a binary number), instants in the organization's timezone (calendar dates `Y-m-d` stay calendar days), readable statuses and plain text.
- **Writers.** `CsvExportWriter` (Phase 7): UTF-8 with BOM, RFC 4180, CRLF, plain decimal strings, `Y-m-d` / `Y-m-d H:i` in the organization's timezone, text starting with `= + - @`, tab or CR prefixed with `'` (formula-injection guard); streamed to a temporary file like xlsx. `XlsxExportWriter` (OpenSpout) streams to a temporary file (`storage/app/private/exports`, deleted after sending): bold frozen header, `NumericCell` with `#,##0.00` for money, `DateTimeCell` for dates, column widths by type, sheet name ≤ 31 characters, `StringCell` for text so nothing becomes a formula. `PdfExportWriter` renders the Blade view `resources/views/exports/list.blade.php` (letterhead, title, filter summary, generated-at and user, `thead { display: table-header-group }` so the header repeats on each page, escaped values) and calls `PdfRenderer::render($html, $landscape, $footerHtml)` — landscape above 6 columns, footer "Page X of Y" from Chrome's `pageNumber` / `totalPages`. PDF rows are collected in memory (bounded by the 2 000-row limit).
- **`PdfRenderer` contract** (`Shared\Application\Export`): HTML in, PDF bytes out; failures throw `PdfUnavailable` (503 `PDF_UNAVAILABLE`), never a raw error. `BrowsershotPdfRenderer` (bound in `AppServiceProvider`) writes the HTML to a private temp directory and runs `spatie/browsershot` with JavaScript disabled, A4, backgrounds, the configured Chrome (`ChromeLocator`: `pdf.chrome_path`, else the newest Playwright Chromium, else system paths), Node, `pdf.node_modules_path` and `pdf.renderer_script` — `backend/pdf-renderer/browser.cjs`, which runs Browsershot's own script with `puppeteer-core` (no bundled Chromium). Tests bind `FakePdfRenderer` and assert the HTML.
- **Letterhead contract** `Shared\Application\Contracts\DocumentLetterhead::forOrganization($id)` → `{name, legal_name, address, phone, email, tax_number, slug, timezone, logo}`. Organizations binds `OrganizationLetterhead` (profile, no logo); Storefront `extend()`s it with `ThemeLogoLetterhead`, which adds the theme logo as a data URI (`MediaLibrary::dataUri()`: a rendition ≥ 240 px wide when one exists, ≤ 512 KB) and never fails the document.
- **Fonts.** Poppins (Latin) and Hind Siliguri (Bengali, Latin fallback), woff2 subsets in `backend/resources/fonts` with OFL licenses; `PdfFonts::css()` inlines them as `@font-face` data URIs with `unicode-range`, so Chrome shapes Bangla without network or file access.
- **Admin.** `components/common/export-menu.tsx` (`ExportMenu list={key} query={…} pathParams={…} disabled={…}`) sends the list's current query (minus `page` / `per_page`) plus `export` to `EXPORTABLE_LISTS[key].endpoint` (`features/exports/lists.ts`) through `lib/api/download.ts`, which mirrors the API client's base URL, cookies, `X-XSRF-TOKEN` and `X-Branch-Id` and turns the blob into an `<a download>`; errors become toasts (`features/exports/errors.ts`). List pages build their query with a shared builder so list and export cannot drift.
- **Libraries.** OpenSpout (MIT) and Browsershot (MIT) with puppeteer-core (Apache-2.0); mPDF was rejected (GPL), Dompdf (no Bangla shaping).

### Business dates and the organization's timezone

The application clock and stored timestamps are UTC (`config/app.php`). A business date that the user picks as a calendar day (GRN invoice and manufacturing dates, supplier payment `paid_on`, expense/income `occurred_on`, COD remittance `received_at`) is compared with **today in the organization's timezone** — `Organizations\Application\Support\OrganizationDate::today()` (`timezone()` falls back to `app.timezone`) — never with `now()->toDateString()`. Date-range filters already convert organization days to UTC bounds. Before X1 the checks used the UTC date, so between 00:00 and 06:00 Asia/Dhaka a date of "today" was refused.

## 3q. Supply chain: supplier catalog and replenishment (SC1)

Slice 1 of the supply chain track; SC2 adds purchase requisitions with approvals and RFQ / quote comparison (§3r), SC3 landed cost and supplier performance (§3s).

- **Ownership.** Purchasing owns what is bought and from whom: the supplier catalog (`supplier_products`, `ManageSupplierCatalog`), reorder suggestions (`Application\Queries\ReorderSuggestions` + the pure `Domain\Reorder\ReorderCalculator`), the actions that turn them into documents (`CreateReorderPurchaseOrders`, `CreateReorderTransfer`) and the daily alert (`purchasing:reorder-notifications`, `reorder_notification_runs`). Inventory owns what a store should hold: per-store reorder rules (`stock_reorder_rules`, `ManageReorderRules`), the organization's replenishment settings (`replenishment_settings`, `UpdateReplenishmentSettings`; own table, not organization settings) and the `ReplenishmentData` contract that hands Purchasing its stock-side inputs. Products keeps `reorder_level` (fallback minimum and the low-stock alert, §3b, unchanged).
- **Pure calculator.** `ReorderCalculator::calculate(ReorderInput): ReorderSuggestion` takes decimal strings and integers only — no database, no clock — and is unit-tested on its own (`ReorderCalculatorTest`, 19 cases). `reorderPoint()`, `surplus()` and `orderQuantity()` are reused for the source store and pack rounding. All arithmetic goes through `Shared\Domain\ValueObjects\Decimal` (new `ceil`, `floor`, `min`, `max`), never floats. Formula: [API_DOCUMENTATION.md § Supply chain](API_DOCUMENTATION.md#supply-chain--supplier-catalog-reorder-suggestions-and-replenishment-sc1).
- **Data sources.** `ReplenishmentData::storeInputs()` (Inventory, `EloquentReplenishmentData`) aggregates the module's own tables: on hand from `stock_levels` (all batches), in transit from `in_transit` transfer lines into the store, net units sold from `stock_movements` (sales and web orders minus cancellations and returns, rolling `velocity_days`, floored at 0) and the effective rule (active rule, else `product_variants.reorder_level` read-only, no maximum). Purchasing adds open order quantities (`ordered` / `partially_received`, outstanding = ordered − received; drafts reported separately as `draft_on_order`, not counted), the preferred catalog row (active row of an active, non-archived supplier through `SupplierDirectory`) and the cost fallback (catalog → last goods receipt line → variant purchase price). Variant facts (tracked, sellable, whole units, names) come from `ProductDirectory`. The query runs the calculator once without a source, then again with the source store's surplus for the variants that need something.
- **Transfer dispatch decision.** Transfers have no draft state (§3b: dispatch → in transit → receive), so a replenishment transfer is **dispatched immediately** through Inventory's `TransferStock::dispatch(…, allocateBatches: true)` rather than adding a draft status to transfers. With `allocateBatches`, lines without a batch are allocated by the ledger first-expiry-first-out (`StockChange::allocateBatches`) and the transfer gets one line per batch taken, so the destination receives the same batches at the cost that left. The user must have access to the source store's branch (`SOURCE_STORE_NOT_ACCESSIBLE` otherwise); stock is checked under the ledger's row locks (`INSUFFICIENT_STOCK`). Purchase orders, by contrast, are created as **drafts** (one per supplier, through `SavePurchaseOrder`) — nothing is committed to a supplier until someone places them.
- **Preferred supplier.** At most one per variant: the action locks the variant's catalog rows and unsets the old preferred row in the same transaction; the partial unique index `(organization_id, variant_id) WHERE is_preferred` and the PostgreSQL CHECK `NOT is_preferred OR is_active` back it in the database. Goods receipts (`PostGoodsReceipt`) write `last_purchase_cost` / `last_purchased_at` on the supplier's existing catalog rows inside the receipt transaction; they never create rows.
- **Scheduler.** `purchasing:reorder-notifications` runs **hourly** (`withoutOverlapping`) and handles an organization from 07:00 in its own timezone (`OrganizationDirectory::activeIds()`, `summary()['timezone']`), so one schedule serves every timezone. Per active store (`BranchDirectory::activeStores()`) it computes the suggestions inside `TenantContext::runAs()`, claims `(store_id, run_on)` with an insert-or-ignore on a unique key, and sends one database notification (`purchasing.reorder_needed`, link `/purchasing/reorder?store_id=…`) to the holders of `purchases.manage` in the store's branch (`UserDirectory::withPermissionInBranch`). Stores with nothing to reorder are not claimed; an exception in one store is reported and the run continues.
- **Idempotency and transactions.** Both creation endpoints use the `idempotent` middleware (`Idempotency-Key` required) and run in one transaction: every draft order or the transfer, or nothing.
- **New cross-module contracts.** `BranchDirectory::activeStores()`, `OrganizationDirectory::activeIds()`, Inventory `ReplenishmentData`; `TransferStock::dispatch()` gains `allocateBatches`. The catalog list (Purchasing) and the reorder-rule list (Inventory) join `product_variants` / `products` read-only to sort and search by product (the documented read-model exception, §2).
- **Admin.** `src/features/supply-chain`: *Purchasing → Reorder* (`/purchasing/reorder`, `purchases.view`), the supplier page with its *Catalog* tab (`/suppliers/:supplierId`; the tab needs `purchases.view`), *Inventory → Settings* with the *Replenishment* card (`/inventory/settings`, `inventory.manage`), the product editor's *Suppliers* and *Reorder rules* panels, and catalog hints in the purchase order editor (cost prefill only into empty or auto-filled costs, pack and minimum hints). `quantities.ts` does pack / minimum rounding and line estimates on decimal strings (no floats); writes are gated by `purchases.manage`, `inventory.manage` and `inventory.transfer`; creation requests keep their `Idempotency-Key` across retries.

## 3r. Supply chain: requisitions, approvals and supplier quotes (SC2)

Slice 2 of the supply chain track (SC3: landed cost and supplier performance, §3s). All in the Purchasing module; endpoints and shapes: [API_DOCUMENTATION.md § SC2](API_DOCUMENTATION.md#supply-chain--purchase-requisitions-approvals-and-supplier-quotes-sc2).

- **Approval policy (pure).** `Domain\Procurement\ApprovalPolicy` takes money strings only: `level(amount, auto, manager)` → `ApprovalLevel` `none|manager|high` (boundaries to the lower tier; auto > manager is refused), `preApprovalCeiling(approved)` = approved × 1.05 (2 dp), `withinPreApproval()`, `share(lineTotal, part, quantity)` (the approved estimate of part of a line). `ApprovalLevel::approverPermissions()` (`manager` → `purchases.approve` or `.approve_high`; `high` → `.approve_high`). Unit-tested on its own (`ApprovalPolicyTest`, 10 cases). The amount is the estimate (requisitions) or the order total incl. tax, in the base currency.
- **Single-step tiered approval.** The amount chooses the permission; one approval by an eligible approver completes the document — there is no chain of approvers (a later slice). `Application\Services\ApprovalRules` reads the settings (`purchase_approval_settings`, defaults until saved) and decides eligibility: the level's permission (Gate), access to the document's branch (`TenantUser::canAccessBranch`) and not an owner (requester; for orders creator and submitter). Self-approval is refused for everyone, including the Organization Admin, and backed by PostgreSQL CHECKs. Recipients for notifications come from `UserDirectory::withPermissionInBranch()` per permission, minus the owners.
- **Level fixed at submit.** Submitting stores `approval_level`; approving uses the stored level, so a limit change never moves a document already waiting. A requisition at `none` is approved in the same transaction by the system (`approved_by` NULL, history actor NULL, no notification).
- **Purchase order approval.** `ChangePurchaseOrderStatus::approvalNeeded()` is the one rule for `submit`, `place` and the PO document's `submit_requires_approval`: no approval when `require_po_approval` is off, the total is within the auto limit, or the order is **pre-approved** (`approved_amount` set by a requisition conversion or an RFQ award for an approved requisition) and its total ≤ the pre-approval ceiling. Otherwise `submit` moves it to `pending_approval` and `place` refuses (`APPROVAL_REQUIRED`) — the existing "mark ordered" path stays for documents that need no approval, so pre-SC2 flows and tests keep working. Rejection returns the order to `draft` with the reason; the pre-approved amount stays, so an edited order is checked again on the next submit.
- **Pre-approval ceiling.** A requisition approval covers the purchase orders made from it: each order carries the requisition's estimate of the quantities it covers (Σ `share()`), and may cost up to 5 % more (catalog or quoted prices differ from estimates) without a second approval. Above that the order needs approval at its own level.
- **Release of quantities.** `RequisitionQuantities` keeps `converted_quantity` and the status in step inside the caller's transaction: a requisition is `converted` once every line is fully turned into POs or handed to an RFQ; an RFQ that is closed, cancelled or awarded for less gives the rest back (`release()`), reopening a `converted` requisition as `approved` (system history row). Cancelling a purchase order linked to requisition lines (`purchase_order_lines.requisition_line_id`, set by conversion and RFQ awards) gives the unreceived quantity back the same way (`releaseFromOrder()`); editing a converted draft's quantities does not adjust `converted_quantity`.
- **RFQ flow.** `SaveRfq` (blank or from requisition lines — then lines and store are fixed), invite while draft or sent, `SendRfq` (≥ 2 suppliers, a line, reply-by): every invited supplier is issued the request; `Infrastructure\Documents\RfqDocument` renders the supplier's PDF (view `purchasing.rfq`, X1 `PdfRenderer` + `DocumentLetterhead`, A4 portrait, quantities only — never prices) and suppliers with an e-mail address (`SupplierDirectory::contacts()`) get `RfqRequestMail`, a queued mail notification sent on demand with the PDF base64-encoded in the job. PDFs are rendered inside the send transaction, so a renderer failure (503 `PDF_UNAVAILABLE`) sends nothing; mails are dispatched with `DB::afterCommit`. Others are flagged *send manually* and the PDF is downloaded per supplier. `RecordSupplierQuote` stores what staff type in (no supplier portal), replacing an earlier answer. `AwardRfq` creates one draft PO per supplier through `SavePurchaseOrder` (server totals, numbering, audit), writes append-only `rfq_awards`, optionally upserts the SC1 catalog through `ManageSupplierCatalog`, and releases unawarded requisition quantities.
- **Comparison (pure).** `Domain\Procurement\QuoteComparison::compare()` takes lines, supplier answers, currency and today: line totals = requested quantity × unit price (`Money::ofProduct`, tax-exclusive) so suppliers compare on the same quantity, `partial` when less is offered, `lowest_price` (ties flag all), `fastest` (shortest stated lead time), `expired`, per-supplier totals and coverage. Unit-tested (`QuoteComparisonTest`).
- **Status history and audit.** `ProcurementHistory` appends `{from, to, note, actor}` rows for requisitions, orders (also on creation and receipts) and RFQs; history tables and `rfq_awards` are append-only (PostgreSQL triggers + `AppendOnly` model trait). Every transition is audited (`purchase_requisition.*`, `purchase_order.submitted|approved|rejected|ordered|cancelled`, `rfq.*`, `purchase_approval_settings.updated`).
- **Transactions and idempotency.** Each transition runs in one transaction under the document's row lock and re-checks the status there; transition routes use the `idempotent` middleware. Notifications (`ProcurementNotifier`, `ProcurementNotification` with a per-type `databaseType`) are sent after commit.
- **Scheduler.** `purchasing:rfq-reminders` runs hourly (`withoutOverlapping`), from 07:00 in each organization's timezone, claims `(rfq_id, run_on)` in `rfq_reminder_runs` and notifies the RFQ's creator once per local day while invited suppliers have not answered after the reply-by date.
- **Visibility.** Requisitions: `purchases.view` and the approve permissions see every requisition of their branches; holders of only `purchases.request` see their own (others → 404). RFQs need `purchases.view` to read and `purchases.manage` to change. The approval-settings read is open to any purchasing permission so the UI can show who must approve.
- **New contracts.** `SupplierDirectory::contacts()` (e-mail, contact person, address, active / archived — for documents sent to suppliers), `UserDirectory::active()` (notify a requester or submitter). `ReorderSuggestions::lastPurchaseCosts()` is public for cost estimates; orders `pending_approval` count as drafts (`draft_on_order`) in reorder suggestions.
- **Admin.** `src/features/procurement` (`api.ts` — every transition with an `Idempotency-Key` kept across retries; `procurement.ts` — badges, who may approve (no self-approval, whatever the API says), timelines, open quantities, default award to the lowest price capped at the quantity offered). Purchasing tabs are gated per permission (requesters and approvers may lack `purchases.view`); a *Requisitions* sidebar entry (`NavItem.unless`) serves them.

## 3s. Supply chain: landed cost and supplier performance (SC3)

Slice 3, the last of the supply chain track. Purchasing owns charges, vouchers and the scorecard; Inventory owns the value-only adjustment; Expenses books the expensed share. Endpoints and shapes: [API_DOCUMENTATION.md § SC3](API_DOCUMENTATION.md#supply-chain--landed-cost-and-supplier-performance-sc3).

- **Allocation (pure).** `Domain\LandedCost\LandedCostAllocator::allocate(charges, lines, currency)` spreads each charge on its own over the lines by line subtotal (`value`) or base quantity (`quantity`) with `Money::allocate` (largest remainder, ties to the earlier line), so every charge's parts add up to the cent; a `value` charge over lines all worth 0 falls back to quantity. `landedUnitCost()` = round(unit cost + landed cost ÷ quantity, 4); `split()` divides a line's amount between on-hand and consumed quantity, exactly. Unit-tested (`LandedCostAllocatorTest`); the admin repeats the same rules in `features/landed-cost/allocation.ts` (BigInt) for the receipt editor's live preview — the server's figures are the ones stored.
- **Charges on the receipt.** `PostGoodsReceipt` allocates the charges before its transaction, stores them (`goods_receipt_charges`, append-only) and posts every line to the `StockLedger` at its landed unit cost, so the weighted average and batch levels include freight and duty from the start. Charge tax is recoverable: owed, not capitalised.
- **Payables model.** There is no separate charge document: a charge without a charge supplier raises the receipt's `payable_total`; a charge with one is a payable of that supplier, read by `SupplierAccount` from `goods_receipt_charges` (statement entry `receipt_charge`); a posted voucher is a payable of its charge supplier (`landed_cost_voucher`). Balances and statements stay computed from documents and supplier payments stay on account, so charges are settled like invoices. Vouchers require a charge supplier, so every voucher amount has a creditor.
- **Value-only adjustments: `StockValuation`.** A voucher posted after the goods arrived must raise the cost of stock still on hand without moving quantity. The ledger's valuation (§3b) is Σ quantity × average cost per `stock_levels` row, so adding value V to a level with quantity q > 0 and average a gives (q · a + V) ÷ q (4 dp): quantity unchanged, value + V (up to the rounding of the average), later outbound movements leave at the new average. That is safe, so it was implemented rather than escalated. It is a **separate contract** (`Inventory\Application\Contracts\StockValuation`, `EloquentStockValuation`), not a method on `StockLedger`: the quantity write path stays one small contract and the anonymous `StockLedger` doubles in other modules' tests stay valid. `revalue(list<StockRevaluation>, StockReference)` refuses to run outside a transaction, locks the levels in the ledger's `store|variant|batch` order (so it cannot deadlock with a stock posting), refuses a level without positive stock, updates the average and appends one movement per level of the value-only type `landed_cost` (quantity 0, `unit_cost` = the per-unit increase, `value` = the value added; a PostgreSQL CHECK keeps `value` exclusive to that type). `StockChange` refuses value-only types, so they cannot enter the quantity path.
- **Attribution: newest stock on hand.** Levels pool units, so `StockValuation::onHandFromDocument()` attributes the stock on hand to a receipt as clamp(level quantity now − quantity posted into the level by other documents after the receipt's movement, 0, quantity the receipt brought) — first in, first out: what came in later is what is still there. `LandedCostCalculator` caps it by the line's received − returned quantity and, when one receipt has several lines on a level, gives it to the last lines first. Exact for batch-tracked lines whose batch nothing else fills; an assumption for pooled levels. Untracked products have nothing on hand.
- **Posting a voucher.** `PostLandedCostVoucher` (one transaction, `idempotent` route): lock the voucher (draft only), compute the table with the levels locked (`LandedCostCalculator::calculate(…, lock: true)` — the same code as the preview, so preview and posting agree for the same stock), revalue the on-hand shares per level, record the consumed share as one expense, write append-only `landed_cost_allocations` and the totals, audit. Drafts (`SaveLandedCostVoucher`) validate branch access, a date not after the organization's today, an active charge supplier and receipts of the voucher's branch; their charges and receipts are replaced on each save.
- **On-account expense.** The consumed share (stock sold, used, written off or returned to the supplier) cannot be capitalised, so it becomes an expense "Landed cost on sold stock" through Expenses' `ExpenseRecorder` with the new `on_account: true`: the money is owed to the charge supplier inside the voucher total and leaves through a supplier payment, so the expense writes no payments-ledger entry (no double outflow), carries `method` `bank_transfer` as the expected settlement, shows "On supplier account" and cannot be voided on its own (`EXPENSE_ON_ACCOUNT`) — the voucher owns it.
- **Supplier performance read model.** `Application\Queries\SupplierPerformance` reads Purchasing's own tables only (purchase orders and lines, receipts and lines, receipt charges, posted vouchers, RFQ invitations, quotes and awards) with query-builder aggregates; no writes, no stored metrics. It collects raw facts per supplier from the previous period's start (or the first trend month) to `date_to`, then computes metrics per window in PHP with `Decimal`; the list, the headline and each trend month use the same `metrics()`. Business dates are compared as stored (order, invoice, voucher dates); RFQ send and award timestamps are converted to the organization's date. Branch scope follows the user's branches. The score is pure (`Domain\Performance\SupplierScore`: on time 35, fill 30, returns 15, price stability 10, responsiveness 10; missing metrics re-weight the rest), unit-tested in `SupplierScoreTest`. The list is computed whole (suppliers with activity in the range), sorted in memory and not paginated; the export uses the same rows.
- **Permissions.** `purchases.landed_cost` for voucher writes and the preview (Branch Manager, Inventory Manager, Accountant; Organization Admin through `*`); everything else reads with `purchases.view`; receipt charges ride on `purchases.receive`.
- **Admin.** `src/features/landed-cost` (allocation mirror, charges editor, receipt landed preview and charges detail, receipt picker, voucher form with a debounced server preview, voucher pages; posting with an `Idempotency-Key` kept across retries) and `src/features/supplier-performance` (filters in the URL, score badge, sortable table, supplier *Performance* tab), wired into `features/purchasing` (receipt editor and detail, statement labels), `features/supply-chain` (supplier page tab), `features/inventory` (Purchasing tabs, movement label) and `app/routes.tsx`.

## 3t. Reports and dashboard (Phase 7)

Module `Reports`: read models only, no tables and no writes. The dashboard cache is its only state. Endpoints and formulas: [API_DOCUMENTATION.md § Reports](API_DOCUMENTATION.md#reports-and-dashboard-phase-7).

- **Registry = whitelist.** `ReportRegistry::REPORTS` lists the 18 report classes (17 in Phase 7; `sales_by_customer` added in Phase 8) (`Application/Reports/*`, contract `Application\Contracts\Report`: `definition()` + `run(ReportContext)`).
  - A `ReportDefinition` holds key, title, group, permission, typed `ReportParam`s (`date|entity|enum|integer|boolean`), `ReportColumn`s (type, `cost_sensitive`, `sortable`), default sort, totals, paginated and granularity.
  - `GET /reports` serves the definitions the user may run; `GET /reports/{key}` runs one. Nothing else can run.
  - **Phase 8 natural-language reporting chooses a key and parameters from this registry** (one tool per definition the user may run) and calls the same runner ([§ 9](#9-optional-ai-module-phase-8--ai1)). The model never writes SQL.
- **Read-model exception.** Report classes read other modules' tables directly through the query builder. Going through directories would make filtering and aggregation in SQL impossible. The rules:
  - read-only;
  - always `organization_id` = the tenant, and `ReportContext::scopeBranches()` on the document's branch column;
  - aggregates in the database (`GROUP BY`), never PHP loops over raw document rows;
  - the database groups the rows, and PHP then merges, sorts and pages them. `stock_movements` is the exception: it can be long, so it returns a query that the runner sorts and pages in SQL and that exports stream in chunks.

  `low_stock` (and the dashboard) also calls Purchasing's `ReorderSuggestions` for suggested quantities, which is not a published contract.
- **One pipeline.** `ParameterResolver` validates shape, applies defaults, checks the range (366 days for daily rows, five years otherwise, `RANGE_TOO_LARGE`) and checks entities: ids of the organization, branch or store accessible, else 422. It resolves the branch scope = accessible branches ∩ `branch_id`, and a category with its descendants. `ReportRunner` builds the `ReportContext`, runs the report, strips cost-sensitive keys without `products.view_cost` (`meta.omitted_columns`), validates the sort against visible sortable columns, and pages. The reports page, exports, the dashboard and the Phase 8 AI tools all use this path.
- **One sales definition.** `Support\SalesFacts::aggregate(ctx, dims)` is the only definition of sales. It runs four aggregate queries (POS lines, POS returns, delivered web order lines, refunded web return lines) plus two for delivery income, groups them by any of `day, month, branch, store, product, category, brand, cashier, channel, tax_rate, customer` (`customer` since Phase 8; walk-ins NULL), and merges them per group with `Decimal`. The sales reports, P&L, tax and the dashboard all call it, so their figures agree.
- **Revenue recognition.**
  - POS revenue is recognised at `sold_at` for completed sales. Returns reduce the period in which they are completed (`decided_at`), not the period of the sale. Cancelled sales are excluded entirely.
  - **Online revenue is recognised on delivery** (`delivered_at` of `delivered` orders): goods after discounts, excluding tax. Shipping and COD fees are *delivery income*, shown separately. Refunds reduce the period of `refunded_at`.
  - Net sales exclude tax, including for tax-inclusive organizations.
- **COGS from line snapshots.** Sale and order lines store `cost_total` when the stock ledger posts the goods out, at the weighted average cost of that moment. WAC includes receipt charges and voucher revaluations (SC3), so landed costs reach COGS automatically. COGS = Σ line cost − cost of returned lines that were restocked; written-off returns stay in COGS. COGS is recognised in the same period as the revenue. The on-account expense for landed cost on stock already sold is an operating expense in the P&L, not COGS.
- **Timezones.**
  - Report dates are organization days (`OrganizationDate`). Ranges become UTC instants (local midnight to local midnight after `date_to`) for timestamp columns. Business-date columns (`invoice_date`, `occurred_on`, `voucher_date`) are compared as dates.
  - Grouping by local day or month uses `Support\Sql`. On **PostgreSQL** it uses `to_char(col AT TIME ZONE '<tz>', …)`, which is exact and DST-aware. On **SQLite** (tests) it shifts by the zone's UTC offset at the start of the range, which is exact for zones without DST such as Asia/Dhaka.
  - The timezone is checked against the IANA list before it is inlined, because PostgreSQL treats differently bound GROUP BY expressions as different.
  - Aggregates come back as exact decimal strings and are rounded once in PHP.
- **Permissions and cost.**
  - `reports.view` (operational), `reports.financial` (P&L, tax), `dashboard.view`.
  - Columns marked `cost_sensitive` (cost, gross profit, margin, stock value, purchase amounts) need `products.view_cost` and are removed from rows, totals and exports otherwise. When the default sort is such a column, the first visible sortable column is used instead.
  - P&L and tax are gated by `reports.financial` alone.
- **Dashboard.** `Application\Dashboard\Dashboard` builds KPIs (current vs previous period of equal length; today vs yesterday), the daily trend (POS / online), top products, low stock, recent transactions and the channel and branch splits, all from `SalesFacts` and `LowStock`. The answer is cached through the cache repository (`remember`) for **60 s**. The key is `reports:dashboard:v1` + organization + hash of the **sorted branch scope** + range + today + cost access + web-order access, so one user's figures are never served to a user with other branches or permissions. The TTL is short and does not depend on any data version, so writes need no invalidation hook. Only arrays are cached, so serializing stores are safe.
- **Exports.** `ReportExport` (a `ListExport`) feeds X1's `ListExporter`:
  - the visible columns, `FilterDescription` lines ("Period: … · Branch: …") and stem `report-<key>`;
  - row results become a `RowSource::fromRows()` with a final *Total* row; `stock_movements` streams through `RowSource::fromQuery()`.
  - Excel, CSV and PDF behave the same as on lists.
- **Indexes, no views.** There are no PostgreSQL views or materialized views: the original plan's `v_*` views would duplicate `SalesFacts` and could not apply the per-user branch and cost rules. Seven `(organization_id, status|…, <date>)` indexes on the scanned tables live in the Reports migration ([DATABASE_DESIGN.md § Phase 7](DATABASE_DESIGN.md)). Summary tables can follow after PostgreSQL `EXPLAIN`.
- **Admin.**
  - `src/features/reports`:
    - catalog page grouped by section;
    - report page driven by the definition: filters from `params`, URL-held state, `max_range_days` pre-check, table with `aria-sort` and totals, cost columns hidden with a note, `ExportMenu list="report"`;
    - `pnl-statement` statement layout;
    - `report-chart` for daily and monthly sales.
  - `src/features/dashboard`.
  - `src/components/common/charts`: accessible SVG charts **without a chart library**:
    - `trend-chart`: line or stacked area, one tab stop, arrow keys / Home / End, tooltip on hover and focus;
    - `bar-chart`;
    - `chart-data-table`: a visually hidden table alternative;
    - `chart-utils`: scales, ticks, and series colours as CSS variables `--viz-1..3` chosen for contrast in light and dark.
  - `app/navigation.ts` `homePath()`: the first sidebar entry (*Dashboard*), except till staff (`pos.sell` without any `reports.*`), who land on `/pos`.

## 4. Authentication and authorization

- **Web SPA:** Laravel Sanctum **cookie-based SPA authentication** (session + CSRF via `XSRF-TOKEN`). No bearer tokens in browser storage, so XSS cannot exfiltrate long-lived credentials. The Vite dev server proxies `/api` and `/sanctum` so the SPA is same-origin.
- **Devices and integrations** (e.g. dedicated terminals, scripts): Sanctum personal access tokens with abilities, revocable per device.
- **Online store shoppers** (E7) sign in on a separate session guard, `customer`, never as staff users; see §3g.
- **RBAC (own implementation, no package):** organization-scoped roles map to code-declared permissions; Gates check permissions, never role names. Built-in roles (Organization Admin, Branch Manager, Cashier, Inventory Manager, Accountant) are provisioned per organization and read-only; organizations create custom roles for anything else. **Super Admin** is a platform-level flag (`users.is_platform_admin`, never mass-assignable), not a role: it passes every Gate and can provision/suspend organizations. A custom implementation was chosen over spatie/laravel-permission because permissions are code-declared per module, roles are strictly tenant-scoped, and the feature set needed is ~300 lines.
- **Lock-out guards:** users cannot change their own roles or status; an organization always keeps at least one active Organization Admin (enforced under a row lock); an organization always keeps one active branch.
- **Escalation guard:** nobody can grant more power than they hold — roles may only contain, and users may only be assigned, permissions the acting user has, and users may only edit users whose permissions are a subset of their own (so `users.manage` alone cannot reset an admin's password). Platform admins and system processes are exempt.
- **Credential hygiene:** login failures are indistinguishable for unknown e-mail vs. wrong password (same message, equalised hashing time); every attempt is recorded in `login_activities`; `/auth/*` credential endpoints are rate-limited per account+IP and per IP; password change/reset and deactivation revoke the user's other sessions and tokens.
- **Audit trail:** sensitive actions are written through the `AuditTrail` contract to the append-only `audit_logs` table with before/after diffs (secrets redacted), request id and IP.

## 5. Transactional integrity (critical POS rules)

| Rule | Implementation |
|------|----------------|
| Sale + stock deduction are atomic | Checkout runs in one `DB::transaction`; any failure rolls back sale, payments and stock movements together. |
| No overselling (unless configured) | Stock level rows locked with `SELECT … FOR UPDATE` in deterministic store/variant/batch order (prevents deadlocks); quantity checked after the lock; `INSUFFICIENT_STOCK` unless the branch allows negative stock (implemented in Phase 4, see §3b). |
| Server-side totals | Client sends only product ids, quantities, requested discounts and payments. Prices, taxes, discounts and totals are recomputed from the database with `Money`. |
| Price/discount validation | Discounts checked against product/role limits and active promotions on the server. |
| Idempotency | `Idempotency-Key` header required on checkout, returns and approvals, customer payments, expenses, cash movements, web order steps, the storefront checkout and the supply chain actions and transitions (reorder documents SC1; requisition, purchase order and RFQ transitions SC2, §3r; landed cost voucher posting SC3, §3s); key + scope (staff user, shopper account or guest cart) + request fingerprint stored with the response; replays return the stored response (`Idempotent-Replayed: true`), mismatched payloads get 409, failed attempts release the key (see §3c, §3d, §3h). |
| Immutable history | Posted sales, stock ledger and payment ledger rows are append-only (enforced in code and by database triggers that reject `UPDATE`/`DELETE`). |
| Returns reference original sale | `sale_returns.sale_id` + `sale_return_lines.sale_line_id` FKs; per-line quantity ceilings checked under the sale's row lock; amounts from the invoice line (see §3d). Online returns (E10b): `order_return_lines.order_line_id`, ceilings checked under the order's row lock, restock to the exact `order_line_stock` allocations (see §3l). |
| Decimal types only | `NUMERIC(18,2)` money, `NUMERIC(18,3)` quantities, `NUMERIC(9,4)` rates. No `float`/`double`/`real` anywhere. |
| Concurrency-safe inventory | Row locks + append-only ledger with `balance_after`; PostgreSQL-only tests hold a lock from a second connection and prove the ledger waits and never oversells (`Inventory/Tests/Feature/StockLockingTest`; web checkout: `Orders/Tests/Feature/CheckoutConcurrencyTest`, E8a). Parallel-checkout tests follow in Phase 5. |
| Tax-inclusive / exclusive pricing | Per-organization/branch setting consumed by one pricing service; both modes covered by calculation tests. |

## 7. Asynchronous work

- **Queues** (Redis in staging/production, database driver locally): notifications, report exports, low-stock checks. AI narratives are written synchronously in the request or by the scheduled `ai:daily-insights` (Phase 8). List and report exports (X1, §3p; Phase 7, §3t) are synchronous downloads, bounded by their row limits.
- **Events/listeners:** cross-module reactions; listeners that touch external systems are queued. Events raised inside financial transactions implement `ShouldDispatchAfterCommit` (first one: `StockFellBelowReorderLevel` → queued `NotifyLowStock`).
- **In-app notifications** use Laravel's database channel (`notifications` table, UUID ids, JSON payload with a `type` and an in-app `link` or `url`); the SPA bell polls the unread count every 60 s and opens `url` (else `link`) when it is a same-origin path. E8a: "New online order" (`orders.new_online_order`) to every active user with `web_orders.view`; the order confirmation e-mail is a queued mail notification sent after the placement commits.
- **Scheduler:** daily summaries, expiry alerts, idempotency-key cleanup, cash-register reminders; hourly storefront product stats (E6); daily `cart:prune` of expired guest carts (E7); `orders:expire-pending` every minute (E8a, see §3h). `purchasing:reorder-notifications` hourly, effective once per store and organization-local day from 07:00 (SC1, §3q). `purchasing:rfq-reminders` hourly, effective once per RFQ and organization-local day from 07:00 (SC2, §3r). `ai:daily-insights` every 30 minutes, effective once per organization / branch scope and day from 07:30 organization time (Phase 8, §9).
- **RFQ e-mails** (SC2, §3r) are queued mail notifications with the PDF attached; without a queue worker they are not delivered (the RFQ still shows them as e-mailed).
- Request id is propagated to jobs through Laravel `Context`.

```
  features/<module>/ api.ts (query/mutation hooks), pages/, components/, schemas (Zod)
  lib/            api client, query client, utilities
  stores/         Zustand stores for client-only state (theme, POS cart, terminal session)
  test/           Vitest setup and helpers
e2e/              Playwright specs
```

- **Server state** only via TanStack Query hooks in `features/*/api.ts`; components never call `fetch` directly.
- **Client state** (theme, cart drafts, UI) in Zustand. Server data is never duplicated into Zustand.
- **Forms:** React Hook Form + Zod; server `VALIDATION_FAILED` details are mapped back onto fields.
- **Navigation** lists a module only once it is backed by working endpoints (no placeholder UI).
- The POS terminal is optimized for keyboard and barcode scanners: an always-focused scan field (scanners type the code and press Enter → exact barcode/SKU lookup), shortcuts F2 search, F4 customer, F8 hold, F9 pay; the cart lives in a persisted Zustand store per branch while every amount shown comes from the server's pricing endpoint.
- **Visual theme** lives in `src/index.css` as CSS variables (light on `:root`, dark on `.dark`) mapped into Tailwind with `@theme inline`. Beyond the shadcn tokens it defines `canvas` (page background behind cards), `heading`, `topbar*`, soft status colours (`success`, `warning`, `info` with `*-soft-foreground`) and the shell sizes `--topbar-height` / `--sidebar-width` (utilities `h-topbar`, `w-sidebar`, `md:ml-sidebar`). The shell is a full-width purple top bar over a fixed icon sidebar; cards are flat with a hairline shadow and uppercase titles; status badges use the soft variants (`success`, `warning`, `info`, `soft`, `destructive`). Font: Plus Jakarta Sans (self-hosted via Fontsource, no external font requests). Colour pairs are chosen for WCAG AA text contrast in both themes.
- Receipts print from the browser: the receipt is rendered into a print-only portal with an `@page` size for 58 mm or 80 mm thermal rolls or A4. Cash drawers wired to the receipt printer open through the printer driver's "open drawer on print" setting; browsers cannot drive a drawer directly.

## 9. Optional AI module (Phase 8 / AI1)

Provider-independent, disabled by default, read-only with respect to business data. Full design as built: [AI_INTEGRATION.md](AI_INTEGRATION.md); endpoints: [API_DOCUMENTATION.md § AI](API_DOCUMENTATION.md#ai-assistant-and-insights-phase-8--ai1).

- **Contract.** `AI\Domain\Contracts\LanguageModel::complete(Conversation, tools, CompletionOptions): Completion` with provider-neutral value objects (`Domain\Llm`). Bound per request by `AIServiceProvider`: `AnthropicLanguageModel` (Claude Messages API over Laravel's HTTP client, no SDK), `NullLanguageModel` (AI off / no key: every call → `503 AI_UNAVAILABLE`), `FakeLanguageModel` (tests; `AI_PROVIDER=fake` outside production).
- **Gate.** `AiGate` = `AI_ENABLED` × provider configured × the organization's `ai_settings.enabled`. It implements Shared's `AiFeatures`, so `/auth/me` reports `ai_enabled` without the Authentication module knowing the AI module (default binding `NoAiFeatures`).
- **Tools are the only data path.** `Toolbox::forUser()` builds one tool per registry report the user may run (`ReportRegistry::visibleTo`, run through `ReportRunner::run()` with `ParameterResolver`, branch scope and cost stripping as on the reports page), plus `dashboard_kpis`, `reorder_suggestions` (SC1, `StoreAccess`) and the analytics `sales_anomalies`, `slow_movers`, `shortage_risk`, each behind its permission. Schemas reject unknown keys; a rejected call is a tool error, nothing runs. `ToolLoop` runs server-side, at most `AI_MAX_TOOL_ROUNDS` rounds, then a final call with `tool_choice: none`. No tool writes.
- **Least data.** ≤ 50 rows + totals per tool; phone, e-mail, customer id and code removed; customer names → `Customer #n`; customer insights send segment aggregates only; facts drop product / store / branch ids. `ai_requests` keeps metadata and validated parameters, never questions, answers, prompts or rows.
- **Deterministic first.** `InsightsCalculator` (KPIs vs the previous period, top movers, z-score anomalies, margin drop, return spike, slow movers, shortage risk), `RfmScorer` + `LoyaltySuggestions` and the SC1 suggestions compute every number; the model writes a narrative from them (`NarrativeWriter`). Insight pages never fail because of AI: facts with `narrative: null` and a `narrative_status`.
- **Metering.** `AiRunner` wraps every model-backed request: gate (off → 503, not logged) → monthly budget (`UsageMeter`, organization month; over → `429 AI_BUDGET_EXCEEDED`) → call → one `ai_requests` row, also on failure.
- **Caching.** Closed-period business insights per organization or branch scope × day × cost visibility in `ai_insights` (computed by `InsightsReader`, a permission-limited non-person reader), filled for yesterday by `ai:daily-insights` from 07:30 organization time; running periods and multi-branch scopes 15 min in the cache store; customer insights 1 h.
- **Cross-module reads.** Reports (`ReportRegistry`, `ReportRunner`, `Dashboard`; new `SalesFacts` `customer` dimension and `sales_by_customer` report), Purchasing `ReorderSuggestions` (not a published contract, as in `low_stock`), Inventory `StoreAccess`, Loyalty `LoyaltyBalances` (new contract), Customers `CustomerDirectory`, Branches / Organizations directories. Nothing calls the AI module except through `AiFeatures`.
- **Failure isolation.** Provider errors after retries become `AiUnavailable`; timeouts are per attempt (`AI_TIMEOUT`); no AI call happens inside a business transaction or on a POS write path.

## 11. Key risks

| Risk | Mitigation |
|------|------------|
| Deadlocks under concurrent checkouts | Deterministic lock ordering, short transactions, retry-on-deadlock wrapper, concurrency tests. |
| Tenant data leakage | Global scopes + policies + isolation tests; RLS evaluation in Phase 9. |
| Rounding disputes | Single pricing service, `Money` VO, documented rounding (per line, half away from zero), golden-value tests. |
| Offline POS terminals | Out of scope for v1; terminals require connectivity. Hold/resume drafts are server-side. |
| Very new toolchain (TS 7, Vite 8, React Router 8) | Pinned lockfiles; upgrade only with green test suite. |
| AI misuse | No SQL generation; tools generated from the report registry and the user's permissions, scope-checked by `ParameterResolver` / `StoreAccess`; no write tools; least-data payloads; monthly token budget per organization; prompts treat data as data. |
