# E-commerce Implementation Plan

Phases are numbered **E1–E14** so they never collide with the POS roadmap (Phases 1–10 in the README). Each phase ends with: app running, backend + frontend tests green **on PostgreSQL**, Playwright for the slice, docs + CHANGELOG updated, and a checkpoint with the owner before the next phase.

## 1. Re-ordering versus the brief

The brief puts "admin management" (its Phase 10) and "CMS, banners, navigation, homepage builder" (its Phase 11) **after** the storefront pages. That conflicts with two non-negotiables: the storefront may not show hardcoded content, and no UI ships without working endpoints. So every phase below is a **vertical slice**: migration → module → admin screen → storefront UI → tests. The brief's Phases 10/11 become hardening/expansion phases rather than the first time admin exists.

### E6 delivery notes (2026-10-31)

- Shipped section types: `product_carousel`, `product_grid`, `product_tabs`, `category_strip`, `brand_strip`. **`category_showcase` and `category_tabs` are not built**: `product_tabs` with category sources covers category tabs, and the category strip covers the showcase. Sources: hand-picked, featured, new arrivals, best sellers, on sale, category (with subcategories).
- Not in E6: rating sort, rating summary and review UI (E10, with reviews); add to cart and wishlist (E7); hot deals (E8); JSON-LD, sitemap (E12a) and translations (E12b). The product page and cards carry no placeholder buttons for these.
- "Frequently bought together" is manual curation per product; computed co-purchase recommendations come with E13. Related products fall back to up to eight newest live products of the same category when no hand-picked related product is live; frequently bought has no fallback.
- Prices are the stored variant selling prices; in exclusive tax mode the storefront says "Excl. VAT" and tax is added at checkout (E8). Availability comes from the new storefront fulfilment store; quantities are never public (`low_stock` at 1–5).
- The listing is filtered, faceted and sorted in PHP over the live candidate set (identical on SQLite and PostgreSQL; sized for a few thousand published products per organization) — E12 revisits it with `EXPLAIN`. Search is `lower(...) LIKE` on name, SKU and brand with a `pg_trgm` index on PostgreSQL, without similarity ranking. `product_stats` counts net units (completed sales minus completed returns) and is refreshed hourly.
- Menus link to categories and brands (by id; hidden or inactive targets drop out). Storefront URLs: `/shop`, `/search?q=`, `/category/{slug}`, `/brand/{slug}`, `/product/{slug}` (`?variant=` for the selected variant).
- Admin: the web listing is a section below the product editor and also a dedicated route `/admin/products/{id}/online-store`, because the Online Store Manager role lacks `products.manage` / `products.view_cost`, which the product editor requires. Attributes live under *Catalog → Attributes*, category and brand listings under *Online store → Categories / Brands*.
- Brief checks 7–10 are covered by the full-stack Playwright test `a product created and repriced in the admin shows its current price everywhere on the storefront` (search listing, product page, shop listing, search suggestions, homepage carousel). The quick view (not part of that test) loads the same `GET /store/products/{slug}` as the product page.

### E7 delivery notes (2026-10-31)

- New modules `CustomerAccounts` (accounts, `customer` guard, sign-up/in/out, verification, reset, profile, password, address endpoints, staff status switch), `Geography` (global divisions/districts) and `Cart` (carts, `CartPricer`, merge, `cart:prune`, wishlists). Addresses are kept by the Customers module; shopper ↔ staff screens meet through contracts (`CustomerOnlineAccounts` declared by Customers, `GuestCartMerger` declared by CustomerAccounts and implemented by Cart).
- **Registration never links POS customers** (ADR-018): every sign-up is a new `CUS-` customer; the phone goes on it only when no other customer uses it. Linking or merging online and POS customers by staff is a later phase.
- Sessions on storefront hosts come from the new `storefront.session` middleware (bootstrap, account, cart, wishlist; catalog/CMS/geo stay sessionless); `SANCTUM_STATEFUL_DOMAINS` is unchanged and Sanctum's guard stays `['web']`. Shopper sign-out regenerates the CSRF token without invalidating the session, so a staff session in the same browser survives (tested). Because `auth:customer` changes the default guard, author columns and the audit trail now use `StaffActor::id()` (staff only) instead of `Auth::id()`.
- Password reset uses its own `customer_password_reset_tokens` table instead of a Laravel broker (60 minutes, constant answers, one e-mail a minute per address); a reset signs in, verifies the e-mail and rotates the remember-me token but does not end other sessions. Verification links last 24 hours and use the request's scheme and host. Unverified accounts can sign in and shop; E8 decides whether checkout needs a verified e-mail. **Changing the e-mail address is not built.**
- Geography: `geo_divisions` (8) and `geo_districts` (64) with Bangla names, bundled in the repository (public facts, 2018 spellings, BBS codes). **No upazila/thana table** — no licensed dataset was confirmed — so addresses carry a free-text `area` (≤ 100); E8 shipping zones work at district level. The `/store/geo/areas` endpoint and the staff `/shipping/areas` screen of the API plan wait for that dataset.
- Cart: no stored prices; `CartPricer` reprices on every read and write via `StorefrontCatalog::variantsForCart` + `SaleCalculator`; unavailable/out-of-stock lines stay flagged (`line_total` `"0.00"`), above-stock lines count with what is available; quantities are never changed on read. Limits: 999 per line, 50 lines, whole units unless the unit allows decimals. A cart reserves no stock (ADR-004: stock leaves at order placement). Wishlist: customers on the server (≤ 200), guests in `localStorage` (product id + slug, ≤ 100) merged on sign-in; the storefront saves products, not variants (`variant_id` stays available in the API).
- Rate limits as built: `customer-auth` = staff sign-in numbers (`POS_AUTH_RATE_LIMIT`), `storefront-write` = 60/min per IP and per customer (ADR-015 planned 30/min per IP+cart).
- Admin: no customers-list "Online" column (optional in the plan; list rows do not carry `online_account`); the **Online store account** card sits in the customer account sheet opened from the customers list, with Disable/Enable for `customers.manage`. No new permission.
- Storefront: account area (overview, profile + password, address book), header account menu, wishlist and cart icons, mini-cart drawer, cart page, wishlist page, add-to-cart on product page, quick view and single-variant cards. **No checkout button** and no "Delivery and payment are chosen at checkout" text until E8; **no order history** until E9.
- Exit criteria: "cart totals equal server totals" and "guest → login merge" are covered by `CartTest` and the full-stack test `a guest cart merges into the shopper account at sign-in and its totals match the server` (10/10 full-stack on desktop against a fresh seed). Backend 388 tests (386 pass, 2 PostgreSQL-only skipped on SQLite), Pint clean; frontend typecheck, lint, 272 Vitest tests and build pass; mocked Playwright 40 pass + 2 skipped by design. The PostgreSQL run is still blocked (local `DB_PASSWORD` blank).
- **E8 is split in three** so each checkpoint stays reviewable and nothing waits on external credentials: **E8a** shipping (zones by district, methods, rates, COD fee), checkout and orders (placement transaction with stock posting, idempotency scope change of ADR-014, status machine, e-mails) with **cash on delivery and bank transfer**; **E8b** promotions (automatic discounts, coupons, flash sales, hot-deals countdown section); **E8c** online gateways (SSLCommerz, bKash, Nagad) once their sandbox credentials are available (Q8).

### E8a delivery notes (2026-10-31)

- New modules `Shipping` (zones by district — one zone per district — and methods with flat fee, free-over threshold, COD allowed/fee and ETA), `OnlinePayments` (per-organization configuration of **cash on delivery** and **bank transfer** behind the `PaymentGateway` interface; no online gateway, no gateway UI) and `Orders` (checkout preview and placement, order document, staff workflow, expiry job, e-mail and inbox notification). **No coupon field and no promotions** (E8b); **no SSLCommerz / bKash / Nagad** (E8c — needs sandbox credentials, Q8).
- Brief check 13 (place an order) and 14 (stock deducted exactly once, order visible in history) are covered by `CheckoutTest`, `WebOrderWorkflowTest` and the full-stack test `a guest places a cash-on-delivery order; the admin sees it and stock goes down once`. "History" in E8a is the admin's *Web orders* list and the shopper's confirmation/status page; the customer's own order list is E9.
- Placement as planned (DATABASE_CHANGE_PLAN §4) minus coupons: lock cart → reprice (E7 `CartPricer`, no separate `VariantPriceLoader`) → address, delivery and payment checks → `expected_total` check (`409 TOTAL_CHANGED` with the fresh preview) → `WEB-000001` → `StockLedger` `online_order` from the fulfilment store (never below zero) → order, lines, batch allocations, address, history → cart converted. `CART_HAS_ISSUES` blocks any flagged cart; there is no `CART_CHANGED` code. Delivery and COD fees are added after tax and **not taxed**.
- Order lifecycle `pending_payment → confirmed → processing → shipped → delivered` with cancellation from the first three; `failed` is reserved for gateways and `returned` waits for online returns (E10). COD orders start `confirmed`, bank transfer `pending_payment`. Payment status only `unpaid` / `paid`. **Paid orders cannot be cancelled** until refunds exist (E10). Courier name and tracking number are text on the order until couriers/shipments (E10).
- Payment hold: bank transfer `settings.hold_hours` (1–168, default 48) on the method — instead of the planned `storefront_settings.pending_payment_ttl_minutes` (30 minutes suits gateways, not bank transfers). `orders:expire-pending` runs every minute with `FOR UPDATE SKIP LOCKED` and restocks the exact batches.
- Money: staff confirm a bank transfer (reference required) or record a courier's COD remittance (shipped/delivered COD orders); both go into the payments ledger through `PaymentLedger::recordSystem` (no drawer; cash refused) with source `online_order`. Confirming a COD order's payment or recording COD in the wrong state is `INVALID_STATUS_TRANSITION`; a second payment `ORDER_ALREADY_PAID`.
- Guests: allowed by default (`storefront_settings.guest_checkout_enabled`, admin switch). Guest orders have **no customer record** — `customer_id` NULL and a contact snapshot — so the POS customer list and phone lookup stay clean (ARCHITECTURE_ANALYSIS planned linking guests by phone; not done). Order page access by a random token returned once and e-mailed (sha-256 stored; it does not expire). Unverified shopper e-mails may check out.
- Idempotency scope change of ADR-014 shipped: `customer:{account id}`, guest `cart:{token hash}`, staff unchanged; a guest without a cart gets `CART_EMPTY` from the middleware. The storefront keeps one key per placement attempt.
- As built beyond the spec: `orders.eta_min_days/eta_max_days`, `order_lines.line_subtotal` and `product_slug`, `order_addresses.email` and division/district ids **and** names; the order view's `line_total` is quantity × unit price (the stored tax-inclusive line total stays in `order_lines.line_total`); the preview answers `CART_EMPTY` / `CHECKOUT_UNAVAILABLE` and returns `payment_method: null` for an unusable method; `GET /store/checkout/options` lists only enabled methods; `save_address` is skipped silently when the area is missing or the address book is full; guests sending `shipping_address_id` get a field error. Error details are documented in API_DOCUMENTATION.md (E8a).
- Lead integration changes: `TRUSTED_PROXIES` (`config/trustedproxy.php`) for HTTPS links, the `Secure` cart cookie and per-visitor rate limits behind a TLS-terminating proxy; the deployment guide's sample no longer sets `SESSION_DOMAIN` (it broke sessions on storefront hosts); the notification bell opens `data.url`; Vitest timeouts raised (20 s per test, 5 s for `findBy*`/`waitFor`); full-stack runs need `POS_CHECKOUT_RATE_LIMIT` raised (e.g. 1000).
- Results: backend 415 tests (412 pass, 3 PostgreSQL-only skipped on SQLite), Pint clean; frontend typecheck, lint, 345 Vitest tests and build pass; mocked Playwright 49 pass + 2 skipped by design (one mobile account-cart test was flaky under load and passed on rerun); full-stack Playwright 11/11 on desktop against a fresh seed. **The PostgreSQL run is still blocked** (local `DB_PASSWORD` blank), so `CheckoutConcurrencyTest` (two checkouts for the last unit) and `StockLockingTest` have never run.

### E8b delivery notes (2026-11-01)

- New module `Promotions` (promotions, targets, coupon codes, append-only redemptions, pure `PromotionEngine`, staff API) consumed through contracts by Cart (`PromotionPricing`), Orders (`PromotionRedemptions`), OnlineCatalog and Storefront (`CatalogPromotions`); Promotions depends only on Catalog, Products, Customers and Organizations. **Web only**: the POS ignores promotions.
- Types `percent`, `fixed` (per unit on product scopes), `free_shipping` (order scope only; waives the delivery fee, never the COD fee); scopes `order`, `products`, `categories` (with sub-categories), `brands`; trigger `automatic` or `coupon`; optional schedule, `min_subtotal`, `max_discount`, total and per-customer usage limits; `show_countdown` makes an automatic product-scope promotion with an end a **flash sale**.
- Application rule (decided for E8b, unit-tested): the single best product promotion per line (largest discount; ties → earliest end, then id), then the single best order promotion on the subtotal after product discounts (`min_subtotal` on the subtotal before discounts), then free delivery; tax after discounts through `SaleCalculator` (product discounts as line discounts, the order discount as the invoice discount — ADR-005's one pricing path). A valid coupon beaten by an automatic offer stays on the cart unused (`better_offer`).
- Coupons: one per cart (`carts.coupon_code`), upper-case `[A-Z0-9-]{3,40}` unique per organization regardless of case, bulk generation up to 500 with a prefix. `422 COUPON_INVALID` with `details.reason` (`not_found`, `not_started`, `expired`, `usage_limit_reached`, `customer_limit_reached`, `min_subtotal`, `not_applicable`) — one error code with reasons instead of the planned `COUPON_NOT_APPLICABLE` / `COUPON_LIMIT_REACHED`. A coupon that becomes invalid stays on the cart, ignored, and never blocks checkout. Rate limiter `coupon` (`POS_COUPON_RATE_LIMIT`, default 10/min per customer, else cart, else IP — ADR-015).
- Placement: the promotions with usage limits and the coupon are locked `FOR UPDATE` (sorted) inside the E8a transaction and the cart is repriced under the locks (≤ 3 rounds); a limit reached meanwhile → existing `409 TOTAL_CHANGED`. One redemption per promotion used, `coupons.used_count` incremented; the idempotent replay redeems nothing twice. Per-customer limits: signed-in shoppers by customer, guests by lower-case contact e-mail (checked at placement).
- As built beyond the spec: redemptions also store `customer_id`, `order_number` and `kind`; only limited promotions are locked (unlimited ones never serialize sales); the `better_offer` reason; `show_countdown` on list rows, `id` on coupon rows, the cart's `coupon` in the checkout preview, an optional `coupon_code` when creating a coupon promotion; `orders.coupon_code` only when the coupon was redeemed; coupon list sorted by code by default; cards price one unit (a product promotion whose `min_subtotal` is above the unit price does not show on cards); new config `pos.coupon_rate_limit`.
- Catalog display: cards and the product page show the best live automatic product-scope promotion (badge, promotional price with the base price struck through, countdown chip); coupon promotions never show. The `hot_deals` homepage section (planned in E5, deferred to E8) is built: one flash sale or all of them, countdown to the earliest end, hidden when none runs. Demo: "Juice week" (10 % off Pran, countdown, 7 days), `WELCOME50` (50 off from 500, once per customer), free delivery over 3000, and a *Hot deals* section after the hero.
- Admin: *Promotions* (list, editor with a target picker reusing the E6 pickers, coupons and redemptions tabs), hot-deals editor in the homepage builder, discounts on the web order page. Permissions `promotions.view` / `promotions.manage` (already planned for the Online Store Manager, ADR-016).
- **Not built:** promotions at the POS; freeing a redemption when an order is cancelled or expires (E10 may revisit with refunds); customer groups, stacking flags and priorities; promotional prices in listing filters, facets and sorts (they use the base price; **E12** may index promotional prices); promotion reports (E10).
- Results: backend 447 tests (443 pass, 4 PostgreSQL-only skipped on SQLite — `PromotionConcurrencyTest` is new), Pint clean; frontend typecheck, lint, 401 Vitest tests (60 files) and build pass; mocked Playwright 60 pass + 26 skipped (opt-in full-stack specs and two by design); full-stack: the 6 e-commerce tests pass on desktop against a fresh seed, including `a flash sale and the WELCOME50 coupon lower the price from card to placed order and the admin order`. The 6 POS/back-office full-stack tests failed in this run because of a **pre-existing timezone mismatch** (`config/app.php` timezone hard-coded to `UTC`; between 00:00 and 06:00 Asia/Dhaka the GRN invoice date is "after today" on the server, and a UTC browser breaks the sales list's "today" filter) — not caused by E8b, recorded as an open issue. Full-stack runs now also need `POS_COUPON_RATE_LIMIT` raised. **The PostgreSQL run is still blocked**: the promotion CHECK constraints, the append-only triggers and `PromotionConcurrencyTest` have never run.

### E9 delivery notes (2026-11-01)

- **Order of phases:** E8c (online gateways) stays deferred until the SSLCommerz, bKash and Nagad sandbox credentials are available (Q8); E9 was built first at the owner's request. Nothing in E9 depends on E8c — customer cancellation is limited to unpaid orders.
- Already built in E7 and not rebuilt: profile and password, address book, wishlist, account overview, header account menu. E9 adds order history, order detail with tracking, customer cancellation, re-order ("Buy again") and product reviews with staff moderation.
- **Own orders only:** an order belongs to the account when `orders.customer_id` is the account's customer (set at placement while signed in). Guest orders placed with the same e-mail are **not** attached — e-mail ownership is not proven (decision recorded here; a verified "claim my guest orders" flow could come later).
- Customer cancel: only `pending_payment` or `confirmed` **and** unpaid (paid orders need refunds, E10), else `ORDER_NOT_CANCELLABLE`; `Idempotency-Key` required (shopper scope `customer:{account id}`); it reuses the E8a `CancelOrder::cancelLocked()` path (restock to the exact batches), writes history with the new `order_status_history.actor_type` `customer`, notifies staff (`web_orders.view`) and e-mails the shopper. Re-order goes through the cart service (`ShoppingCart::addLines`): today's prices, merged quantities, skipped lines reported (`unavailable`, `out_of_stock`, `limit`).
- New module `Reviews` (one review per customer and product; rating 1–5, optional title, plain-text body 10–2000; pending → approved / rejected; staff `reviews.view` / `reviews.moderate`). **Verified purchases only:** a review needs a delivered web order line of the product (`REVIEW_NOT_ALLOWED`; asked through Orders' `PurchaseVerifier`) and records it as `order_line_id`; there are no unverified reviews. Orders and OnlineCatalog do not depend on Reviews: they declare `OrderLineReviews` and `ProductRatings`, which Reviews implements. Public author = first name + last initial. Rate limiter `reviews` (`POS_REVIEW_RATE_LIMIT`, 5/hour per customer).
- Product page: rating summary near the title and a *Reviews* tab (summary with distribution, sort, rating filter, pagination). **Product cards show no rating** and there is no rating sort until E10. The summary is an aggregate over approved reviews per request, **uncached** in E9 (adequate for the size target; a projection can come with the E10 rating sort).
- Admin: *Reviews* moderation queue (pending first; approve, reject with a reason, delete; read-only with `reviews.view` only); the web order history shows who acted and "Cancelled by customer". The "reviews moderation" item of E10 is therefore done; review media and the rest of reviews stay for E10.
- As built beyond or instead of the spec: per line `review` + `reviewable` instead of `can_review`, plus `variant_id`; `cancelled_at` / `cancel_reason` on the account detail; `details.payment_status` on `ORDER_NOT_CANCELLABLE`; `actor_type` on the staff history only; customer review list 20 per page; the `reviews` limiter counts refused attempts; no idempotency key for moderation (idempotent by state); review bodies stored as trimmed plain text (clients escape).
- Demo (`DemoAccountSeeder`, through the real services): the demo shopper's `WEB-000001` (2 mango juices, delivered, COD paid, tracking `DEMO-TRK-0001`) with an approved 5-star review, and `WEB-000002` (rice, confirmed unpaid COD, cancellable).
