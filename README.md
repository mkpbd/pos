# Enterprise POS

Multi-organization, multi-branch point-of-sale platform: **Laravel 13** REST API (modular monolith, PostgreSQL 18, Redis) and a **React 19 + TypeScript** SPA (Vite, Tailwind, shadcn/ui, TanStack Query, Zustand).

Correctness of sales calculations, inventory consistency and financial integrity come first: all totals are computed on the server with arbitrary-precision decimals inside database transactions, ledgers are append-only, and checkout/payment requests are idempotent.

## Repository layout

```
backend/    Laravel API — business modules in app/Modules/*
frontend/   React SPA — features in src/features/*
docs/       Architecture, database, API, guides
```

## Quick start

See [docs/DEVELOPMENT_GUIDE.md](docs/DEVELOPMENT_GUIDE.md) for prerequisites and details. The backend requires **PHP 8.4** (`composer.json`: `php ^8.4`). PDF exports also need Node.js ≥ 22.12, `PUPPETEER_SKIP_DOWNLOAD=1 npm ci` in `backend/pdf-renderer` and a Chrome/Chromium (locally Playwright's).

```powershell
# one-time: create role pos_app and databases pos / pos_test
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -h 127.0.0.1 -f backend\database\scripts\create_local_databases.sql

cd backend;  composer install; copy .env.example .env; php artisan key:generate   # then set DB_PASSWORD in .env to the pos_app password
php artisan migrate; php artisan serve
cd frontend; npm install; npm run dev     # admin http://localhost:5173/admin, storefront http://localhost:5173/
```

The demo shopper has three orders under *Orders* in the storefront account area: `WEB-000001` (delivered, with a published 5-star review of Pran Mango Juice), `WEB-000002` (confirmed cash on delivery, still cancellable) and `WEB-000003` (cash on delivery, shipped with Steadfast and in transit); reviews are moderated under *Reviews* in the admin. Couriers Pathao (with a tracking link), Steadfast and RedX are set up under *Online store → Shipping → Couriers*; once `WEB-000003` is marked delivered (*Add tracking update* on the order) it appears under *COD to collect* on the *Web orders* board and can be settled under *COD remittances*. Online returns are accepted for 7 days after delivery (`return_window_days`, set through `PATCH /storefront/settings`): `WEB-000001` can be returned from the shopper's order page (*Return items*); the request appears under *Web returns* in the admin (approve → goods received → refund) and the shopper sees it under *Returns* in the account area. A paid order that is not delivered yet can be cancelled with a full refund from its page in the admin (*Cancel* → refund method; needs `web_orders.refund`). The demo blog (*Content → Blog* in the admin) has the categories *Recipes* and *Store news*, four published posts and one scheduled a week ahead; it is linked as *Blog* in the main menu (http://localhost:5173/blog) and teased in the homepage's *From our blog* section. A popup banner "Free delivery over ৳3000" is seeded **inactive** (switch it on under *Online store → Banners → Popup*). Bank-transfer orders are cancelled when their hold runs out only while the scheduler runs (`php artisan schedule:work`). The demo store is bilingual (English default, Bangla on, Latin digits): the header's *English / বাংলা* switcher (in the mobile menu on small screens) shows the store in Bangla — e.g. http://localhost:5173/?lang=bn — with Bangla category, brand and menu names, five translated products (e.g. *Pran Mango Juice*), banners, homepage section titles, About us / FAQ / Contact, two blog posts, the delivery methods and cash on delivery; untranslated content shows in English. Languages are set under *Online store → Settings → Languages*; Bangla texts are entered in each editor's *বাংলা (Bangla)* section.

Theme demo stores (T2, optional, never in production): after `migrate:fresh --seed` run `php artisan db:seed --class=DemoThemesSeeder` to add four **separate demo organizations**, each a complete store in its own theme preset — *Green Basket* (vegan) at http://vegan.shop.localhost:5173, *Mati & Co.* (handmade) at http://handmade.shop.localhost:5173 *Classic Shop* (classic) at http://classic.shop.localhost:5173 and *Little Sprouts* (kids, BerryKid-inspired) at http://kids.shop.localhost:5173 — with 18–20 products with photos and variants, opening stock, a flash sale, a coupon (`GREEN10`, `MATI15`, `CLASSIC20`, `SPROUT10`), menus, banners, homepage, About / Contact / FAQ / Privacy / Terms pages, blog posts and verified reviews. Admin logins (password `password`): `owner@greenbasket.test`, `owner@mati.test`, `owner@classicshop.test`, `owner@littlesprouts.test`. Real organizations are not touched; re-running skips stores that exist. The demo gallery at http://localhost:5173/demos lists them when `STOREFRONT_DEMO_GALLERY=true`. Local hosts need `TRUSTED_PROXIES=127.0.0.1` (the Vite dev proxy forwards the browser host) and `*.shop.localhost:5173` in `SANCTUM_STATEFUL_DOMAINS` (see `backend/.env.example`); browsers resolve `*.localhost` to this machine without a hosts-file entry. Photo credits: [DEMO_IMAGE_CREDITS.md](docs/ecommerce/DEMO_IMAGE_CREDITS.md).

Exports: 37 admin list screens (sales, returns, payments, expenses, inventory, purchasing — incl. supplier catalog and reorder suggestions (SC1), requisitions, RFQs and the approvals inbox (SC2), landed cost vouchers and supplier performance (SC3) — and statements, products, customers, suppliers, web orders and returns, COD remittances, promotions, reviews, contact messages, newsletter, users, audit log) have an *Export* button — *Excel (.xlsx)*, *CSV (.csv)* (Phase 7) or *PDF* of every row matching the current filters, search and sort, with the organization letterhead on PDFs (Bangla text included); every report exports the same way. The API equivalent is `?export=xlsx|csv|pdf` on the list endpoint ([API_DOCUMENTATION.md § Exports](docs/API_DOCUMENTATION.md#exports-x1)).

Supply chain (SC1): each supplier has a *Catalog* (supplier page → *Catalog*: supplier SKU, unit cost, pack size, minimum order, lead time, one preferred supplier per product; the last purchase cost is filled in by goods receipts), products have per-store *Reorder rules* (min / max) and their suppliers on the product page, and *Inventory → Settings* holds the replenishment settings (central source store, coverage, sales-history and safety days). *Purchasing → Reorder* lists what each store needs from stock, open orders, transfers in transit and sales velocity, and turns the selection into draft purchase orders (one per supplier) or a replenishment transfer from the source store; the purchase order editor prefills catalog costs and pack hints. Purchasing staff get a daily in-app *Reorder needed* alert per store while the scheduler runs. Demo data: Pran sells the mango juice in cartons of 24 (preferred, 3 days), Local Mills the Miniket rice in 25 kg sacks (preferred, minimum 50, 2 days), Pran the rice as an alternative; the main store has rules for juice, rice and the M polo shirt, so a fresh seed suggests buying 144 juices from Pran, 300 kg rice from Local Mills and 18 polo shirts (no supplier). The demo has one store, so no source store is set and nothing is suggested for transfer.

Requisitions and quotes (SC2): branch staff raise *Purchasing → Requisitions* (or *Raise requisition* on the Reorder page, without `purchases.manage`); the estimated total decides who approves — up to 10 000.00 nobody (approved on submit), up to 100 000.00 a manager (`purchases.approve`), above that `purchases.approve_high` — and nobody approves their own document. Approvers work from *Purchasing → Approvals*; approved requisitions are converted into draft purchase orders per supplier (pre-approved for the approved amount + 5 %) and/or a request for quotation. Purchase orders above the auto-approve limit wait for approval after *Save & submit*. *Purchasing → RFQs* invites suppliers, sends a PDF per supplier (e-mailed when the supplier has an address — needs the queue worker), records the quotes staff enter, compares them line by line (lowest price, fastest, totals, coverage) and awards lines (split allowed) into draft purchase orders, optionally updating the supplier catalog. Limits are set under *Purchasing → Settings*. Demo data: `PR-000001` by the cashier (16 036.00, waiting for manager approval in the owner's inbox), `PR-000002` approved and converted into the draft, pre-approved `PO-000002` (Local Mills), and `RFQ-000001` (polo shirts) sent to Pran and Local Mills with Pran's quote recorded.

Landed cost and supplier performance (SC3): the goods receipt editor has a *Charges* section (freight, duty, insurance, handling, other; spread over the lines by value or quantity, optionally billed by another supplier) and shows the landed unit cost per line before posting — stock enters at that cost. Bills that arrive after the goods are entered under *Purchasing → Landed costs* as landed cost vouchers against posted receipts of one branch: the preview shows how much goes into the cost of stock still on hand and how much is expensed for stock already sold; posting raises the average cost, books the rest as an expense on the supplier's account and adds the bill to that supplier's balance. *Purchasing → Supplier performance* scores suppliers 0–100 on on-time delivery, fill rate, returns, price changes and quote responses (default the last 90 days; *Export*), and each supplier page has a *Performance* tab with a 12-month trend and late or short deliveries. Needs `purchases.landed_cost` for vouchers (Branch Manager, Inventory Manager, Accountant, Organization Admin). Demo data: *Dhaka Apparel Sourcing* delivered `PO-000003` late and short as `GRN-000002` (polo shirts L and XL, with sea freight billed by *Sundarban Freight Services* and handling on the invoice; 2 XL returned as `PRN-000001`) and `PO-000004` on time as `GRN-000003`; `LCV-000001` (800.00 customs duty from Sundarban on `GRN-000002`) is posted — 720.00 into stock, 80.00 expensed as `EXP-000002` for the returned shirts — so the scorecard lists Dhaka Apparel Sourcing below 100.

Reports and dashboard (Phase 7): owners, managers, accountants and inventory managers land on the *Dashboard* — net sales, today's revenue, orders, gross profit (with cost access), average ticket and returns against the previous period, a daily sales trend (POS vs online), top products, low stock (→ *Purchasing → Reorder*) and recent transactions, filtered by branch and date range; cashiers still land on the POS terminal. *Reports* lists 18 reports by section — sales (daily, monthly, by product, category, branch, cashier), inventory (valuation, stock movements, low stock, expiry), purchasing (purchases, supplier dues), finance (profit and loss, payment collections, tax, expenses) and customers (sales by customer — Phase 8 — and customer dues) — each with filters from its definition (date presets, branch, store, product, category, brand, cashier, supplier, customer, channel, group by), sorting, totals, pagination, a shareable URL and *Export* (Excel, CSV, PDF). Sales count POS sales and web orders on delivery, net of discounts and returns, excluding tax. Cost, profit and stock-value columns need `products.view_cost`; profit and loss and tax need `reports.financial`. Demo data: 60 days of sales by `manager@demo.test` on register *T3 — Counter 2* (`INV-MAIN-000003`…`278`, returns `RET-MAIN-000001`…`008`) and six delivered cash-on-delivery web orders (`WEB-000004`…`009`) of four products of their own (*Butter Cookies 200g*, *Atta Flour 2kg*, *Bath Soap 100g* with a batch expiring in 12 days, *Dishwashing Liquid 500ml* below its reorder level); the numbers and stock the earlier demo documents use are unchanged.

AI assistant and insights (Phase 8 / AI1, optional, **off by default**): *AI Insights* in the admin answers questions about sales, stock, purchasing and finances in English or Bangla from the reports the user may run (the answer, the report table and an *Open full report* link), shows business insights (daily / monthly figures against the previous period, top movers, unusual sales days, margin drop, return spike, slow movers, shortage risk) and customer segments (RFM: Champions, Loyal, Potential, New, At risk, Hibernating, with masked top customers and loyalty suggestions); *Purchasing → Reorder* gets *Explain with AI*. Every number is computed by the application; the model only writes the text, never writes data and never sees customer names or contacts. With AI off the insight pages still show their figures. To turn it on, set in `backend/.env`: `AI_ENABLED=true`, `AI_API_KEY=<Anthropic API key>` (never commit it) and optionally `AI_MODEL` (default `claude-sonnet-5-5`); `AI_PROVIDER=fake` with `AI_ENABLED=true` shows the screens with a canned answer and no key (not in production). Organization Admins switch AI off for their organization, set a monthly token budget (default `AI_MONTHLY_TOKEN_BUDGET` = 2 000 000) and see usage under *Organization → AI*. Run `php artisan pos:permissions:sync` after pulling (`ai.ask`, `ai.insights`, `ai.manage`). Details: [docs/AI_INTEGRATION.md](docs/AI_INTEGRATION.md).
